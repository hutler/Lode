# Pre-commit-скрипты Lode для агентов

Эти проверки запускает Lode при `validate`, `shelve` и `commit`. Установка Git-хука в `.git/hooks` для этого не требуется. Сервер может независимо проверить содержимое каждой версии полки и потребовать успешный результат перед её принятием. Здесь описано ядро с поддержкой M19. Для установленной сборки проверьте `lode --version` и `lode validate --help`. [Общее руководство агента](agent-guide.ru.md) · [Спецификация, §6.8](../lode/docs/SPEC.md).

## 1. Подключить проверку в депо

Пример проверяет синтаксис изменённых JSON-файлов. Поместите в корень депо файлы из [рабочего примера](../lode/examples/validate/): для этого правила нужны `tools/validate/json_valid.py` и `tools/validate/report.py`. Сохраните их в той же ревизии, что и объявление. Если `.lodeconfig` уже есть, добавьте правило к существующим и дополните соответствующие таблицы.

```toml
# .lodeconfig
[validate]
python = "3.11"
support = ["tools/validate/report.py"]

[[validate.script]]
name = "json"
run = "tools/validate/json_valid.py"
paths = ["**/*.json"]
timeout = "60s"
server = true
```

- `python` в **депо** задаёт минимальную версию. `run` указывает на отслеживаемый файл относительно корня. Отсутствующий в новой ревизии скрипт может вызвать `invalid_request` при записи.
- `paths` отбирает изменённые пути, которые получает этот скрипт. Если ни один не подходит, результат будет `skipped`. Для файла, созданного на диске, предварительно выполните `lode add PATH`.
- `support` перечисляет дополнительные файлы для серверной рабочей директории. Укажите импортируемые модули, таблицы правил и другие данные, нужные проверке. На сервере доступны выбранные изменения и объявленные зависимости. Скрипт, который случайно читает остальное дерево в полной локальной копии, может там упасть.
- `timeout` по умолчанию 60 секунд, максимум 10 минут. `server = true` по умолчанию разрешает серверный запуск при включённом модуле. Серверный check получит имя `validate/json`.

Готовый набор содержит также проверку имён ассетов по таблице TOML и размеров текстур и звука. В этом случае переносите весь набор с его `support` и настройками. [Конфигурация примеров](../lode/examples/validate/.lodeconfig).

## 2. Написать скрипт

Lode запускает `python -X utf8 <run>`. Рабочий каталог — корень рабочей копии либо временное дерево сервера. Агентская авторизация для работы скрипта не требуется. Среда процесса ограничена, установлен `LODE_VALIDATE=1`. Файловые права остаются правами запустившего пользователя. Обрабатывайте только переданные файлы и выводите необходимую для исправления диагностику.

**Вход.** Один JSON-объект в stdin. `phase` принимает `manual`, `commit`, `shelve` или `server`. Каждый элемент `files` имеет `path` и действие `add`, `edit`, `delete` либо `move`. Для переноса может присутствовать исходный путь `from`. При проверке содержимого пропускайте удалённые файлы и читайте новый путь перемещённого файла.

```json
{"version":1,"phase":"manual","depot":"game","branch":"main","files":[{"path":"Data/items.json","action":"edit"}]}
```

**Выход.** Печатайте по одному JSON-объекту на строку stdout. Поля `level` и `message` описывают проблему. Добавьте `path` и, если известно, `line`. Остальной текст сохраняется как текстовая диагностика. Предупреждение с кодом выхода 0 оставляет проверку успешной. Для ошибки в содержимом завершите процесс с кодом 1. Другой ненулевой код, тайм-аут или необработанное исключение означают ошибку самой проверки.

```json
{"path":"Data/items.json","line":2,"level":"error","message":"Expecting property name enclosed in double quotes"}
```

За образец реализации возьмите [json_valid.py](../lode/examples/validate/tools/validate/json_valid.py) и [report.py](../lode/examples/validate/tools/validate/report.py). Первый обрабатывает синтаксис и кодировку, второй формирует отчёт и код выхода. Для собственного правила проверьте как минимум корректный файл, ошибочный файл, удаление и ситуацию без совпадающих путей. Для правила о переносах добавьте проверку старого и нового имени.

## 3. Локальное доверие и Python

Прочитайте `.lodeconfig`, код всех перечисленных скриптов и их зависимостей. Локальное доверие учитывает сервер, депо, путь скрипта и отпечаток его содержимого. Отдельный отпечаток импортируемого файла в эту запись не входит. Проверяйте изменения зависимостей при ревью. Команда владельца рабочей машины после ревью:

```sh
lode validate --trust
```

Она запоминает **все текущие доступные скрипты депо** и проверяет подходящие изменения. После изменения содержимого основного скрипта требуется новое доверие. В режиме `--json` при отсутствии доверия Lode возвращает `validation_untrusted` с `details.scripts`. Передайте владельцу список файлов для проверки. Локальный MCP предоставляет проверку, а выдача доверия остаётся у владельца.

Клиент ищет Python сначала по `LODE_PYTHON` (путь к программе), затем по `[validate].python` в пользовательском `settings.toml`, затем по системным именам. В Windows порядок — `py -3`, `python`, `python3`. В Linux и macOS — `python3`, `python`. Пример для агентской машины с Windows, где отсутствие интерпретатора должно остановить операцию:

```toml
# settings.toml
[validate]
python = ["py", "-3.11"]
missing_python = "refuse"
```

По умолчанию клиент предупреждает об отсутствии подходящего Python и пропускает запуск. Поэтому даже при `ok: true` читайте `results[].outcome` и `reason`. Пустой `results` означает, что ни один результат проверки не получен.

## 4. Проверить локально и устранить отказ

```sh
lode --json status
lode --json validate --script json Data/items.json
lode --json validate -c content-fix
```

Последнюю команду используйте, если правки входят в changelist `content-fix`. Затем `commit` или `shelve` проверит свой фактический набор изменений повторно. В локальном MCP у инструмента `validate` доступны аргументы `paths`, `changelist` и `script`. Например, вход для одного файла:

```json
{"paths":["Data/items.json"],"script":"json"}
```

| Ответ | Что проверить и как продолжить |
| --- | --- |
| `ok: true`, `passed` | Скрипт выполнился. Проверьте предупреждения в `results[].problems` |
| `ok: true`, `skipped` | Прочитайте `reason`, проверьте добавление файла, glob, changelist и версию Python |
| `validation_untrusted` | Выпишите `details.scripts`. Владелец может выдать доверие после просмотра |
| `validation_failed`, `outcome: failed` | В `error.details.results[].problems` найдите файл, строку и сообщение. Исправьте содержимое и повторите тот же вызов |
| `validation_failed`, `outcome: error` | Прочитайте `reason` и `text` результата. Проверьте импорт, доступность файлов, исключение и тайм-аут |
| `python_missing` | Сверьте требуемую версию в депо, выбранный исполняемый файл и настройки запускающего пользователя |

При отказе локальной проверки отправка останавливается до создания полки или коммита. CLI поддерживает `--no-verify` для пропуска локального запуска. MCP не предоставляет этого параметра. Пропущенный запуск нельзя указывать в отчёте как успешный. Обязательные серверные проверки полки продолжают действовать.

## 5. Включить проверку полок на сервере

Администратор включает модули и выбирает интерпретатор **на сервере**. Пример фрагмента для Linux с доступным сервису Python 3.11. Объедините значения с действующими таблицами `loded.toml`:

```toml
# loded.toml
[modules]
shelves = true
checks = true
validate = true

[validate]
python = "/usr/bin/python3.11"
```

В депо задаётся политика веток. Для проверки каждой принимаемой правки в `main` используйте обе настройки:

```toml
# .lodeconfig
[branches]
shelf_only = ["main"]

[checks]
branches = ["main"]
```

Для новой версии полки сервер берёт **список правил, скрипты и support-файлы из вершины целевой ветки**, а проверяемые изменения — из полки. Поэтому полка с изменённым валидатором проходит серверную проверку по прежнему правилу. Новый валидатор проверьте локально на положительном и отрицательном примере, затем после его принятия создайте новую тестовую полку. В её checks должен появиться результат нового правила.

Проверки публикует сервисный пользователь `lode-validate`. На ветке из `[checks].branches` при принятии нужны успешные серверные проверки совпавших правил плюс явно обязательные внешние checks. `[branches].shelf_only` направляет обычные прямые коммиты через полки. Без включённого серверного модуля локальный успех сам по себе серверное исполнение не подтверждает.

## 6. Проверить всю цепочку

1. В тестовом депо с принятым правилом измените отслеживаемый `Data/items.json`, оставив незакрытую скобку. Выполните `lode --json validate --script json Data/items.json`. Ожидаются код выхода 1, `validation_failed`, путь и строка. Убедитесь через `status`, что правка осталась на диске.
2. Исправьте JSON и повторите ту же команду. Ожидаются `passed: true` и результат `json` с `outcome: "passed"`. Отправьте проверенный файл через `lode --json shelve Data/items.json --keep -m "Check JSON validation"` и сохраните `shelf` и `version`.
3. Подставьте эти значения в `lode --json checks ID@VERSION`. Дождитесь `validate/json` со статусом `success`. По HTTP полная диагностика доступна с правом `read` на `GET /api/v1/depots/{depot}/validate/{shelf}/{version}`.
4. В отчёте укажите локальный результат, идентификатор и версию полки и серверный результат по имени. Если полка обновилась, проверьте новую версию отдельно. При `checks_required` найдите отсутствующую или упавшую проверку в `details.missing`.

Для разработки самого Lode предусмотрен сквозной тест примеров: из `lode/` выполните `cargo test -p lode-cli --test validate_examples` с доступным Python 3.11+. Он проверяет ошибочные данные на клиенте и сервере. Отдельный набор покрывает защиту от подмены скрипта в полке, тайм-аут и восстановление после остановки сервера. [Тест примеров](../lode/crates/lode-cli/tests/validate_examples.rs) · [Серверные сценарии](../lode/crates/lode-cli/tests/server_validate.rs).
