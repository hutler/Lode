# Работа агента с Lode

Руководство для агента, который получает задачу в депо Lode, готовит изменение и передаёт его на проверку. В примерах `game` — депо, `main` — ветка, `content-fix` — локальный список изменений. Подставляйте значения своей задачи. Команды с файлами запускайте из корня рабочей копии. Подробности написания и подключения проверок вынесены в [руководство по pre-commit-скриптам](agent-validation.ru.md).

## 1. Что хранит Lode

**Депо** содержит ветки, ревизии, содержимое файлов и серверные полки. Номер ревизии выдаётся на всё депо. Каждая ветка имеет свою вершину. Успешный `commit` сразу создаёт серверную ревизию. Если другой участник изменил файл, на котором основана ваша правка, сервер может отклонить запись с `out_of_date`.

**Рабочая копия** связывает каталог на диске с сервером, депо и веткой. В ней живут локальные правки, конфликты и именованные списки изменений (*changelists*). Её *view* определяет, какие пути материализуются на диске. Отсутствие файла на диске ещё не доказывает его удаление в депо. Учитывайте view и статус файла.

**Полка** (*shelf*) сохраняет предложение на сервере. У неё есть идентификатор, владелец и версия. Каждая переработка создаёт новую версию той же полки. При принятии полки ревизия сохраняет автора предложения и того, кто её принял. Эти два имени могут различаться.

## 2. Выбор интерфейса

| Где работает агент | Интерфейс | Типичная задача |
| --- | --- | --- |
| Доступен локальный диск | `lode --json` | Checkout, просмотр состояния, правка файлов внешними инструментами, локальная проверка и полка |
| MCP-клиент рядом с рабочей копией | `lode mcp -C /work/game` через stdio | Те же файлы, локальные diff и конфликты. Инструмент `validate` проверяет выбранные правки |
| Доступен только сервер | HTTPS на `/mcp` | Читать файлы нужной ревизии и предлагать изменения через `create_shelf` и `update_shelf` |
| Результат принимает человек | Lode Desk | Открыть полку, посмотреть diff и результаты checks. Полезно приложить ссылку из ответа `shelve` |
| Работа идёт в Unreal Editor | Lode for Unreal | Рабочие файлы проекта, блокировки, sync и submit через установленный CLI |

Наличие инструмента MCP зависит от токена и включённых серверных модулей. При подключении запросите список инструментов и их входные схемы. У локального процесса stdio зарезервирован под протокол. Примеры подключения и ограничения размера запросов приведены в [справочнике MCP](../lode/docs/MCP.md).

## 3. Начало сессии

Используйте отдельную учётную запись агента с владельцем. Права складываются из scope токена и правил доступа к депо, веткам и путям. Агент не наследует доступ владельца. По умолчанию токен агента имеет scopes `read`, `shelve`, `lock`. Возможность прямой записи требует `write` и разрешения на целевую ветку. Для автоматизации укажите путь к выданному файлу токена в `LODE_TOKEN_FILE`. В отчёт заносите имя из `whoami`, без содержимого токена.

Если рабочая копия ещё не создана, выполните `lode checkout https://lode.example.com/game game` и перейдите в каталог `game`. В существующей копии начните с чтения:

```sh
lode --json --version
lode --json whoami
lode --json view show
lode --json status --remote
lode --json diff --stat
```

Сохраните имя сервера, ветку, базовую ревизию и исходный список изменённых файлов. Это позволяет отличить результат задачи от уже существующих правок. При проблеме соединения `lode doctor` покажет, на каком этапе возникла ошибка (DNS, TLS, API или авторизация). При запуске локального MCP можно передать `--agent-model`, `--agent-tool` и `--agent-session` для записи происхождения предложения. Права по этим меткам не выдаются.

## 4. Правка в рабочей копии

1. Посмотрите `status --remote` и `diff` по затронутым путям. Если нужен новый базовый снимок, выполните `lode update` и проверьте список конфликтов.
2. Перед редактированием файла, требующего блокировки, проверьте `lode locks` и возьмите блокировку через `lode lock Content/Hero.uasset -m "Update collision"`. При чужой блокировке уточните владельца. Для переносов и копий используйте `lode mv` и `lode cp`, чтобы сохранить связь с историей исходного пути.
3. Файлы под управлением Lode проверяются при сканировании. Новые файлы явно добавьте через `lode add`, удаление зарегистрируйте через `lode rm`. Статус `missing` требует выяснить, почему исчез файл.
4. Соберите в changelist только пути задачи. Пример ниже предполагает, что вы уже изменили отслеживаемый файл `Data/items.json`. Опция `--keep` оставляет локальные правки после создания полки.

```sh
lode changelist new content-fix -m "Fix item definitions"
lode changelist move content-fix Data/items.json
lode --json diff Data/items.json
lode --json validate -c content-fix
lode --json shelve -c content-fix --keep -m "Fix invalid item definitions"
```

Из ответа сохраните `shelf`, `version` и `link` (когда доступна). Если вы оставили файлы для следующей итерации, проверьте их через `status`. Для поправки уже открытой полки используйте `shelve --update ID` с актуальным набором изменений и описанием. Отдайте рецензенту новый номер версии.

## 5. View, переключение ветки и слияние

Перед сужением view посмотрите `view show`, `status` и diff по исключаемым путям. Если операция сообщает о локальных изменениях, сохраните работу в полке или согласуйте её дальнейшую судьбу. После изменения view ещё раз сверьте список путей и правки. Не используйте `revert --all` для устранения этого отказа.

Уточните целевую ветку по `status`, доступные ветки и их связи по `lode branch tree`. Команда `switch` переносит рабочую копию на другую ветку, а `merge SOURCE` применяет изменения из SOURCE к текущей ветке. У типизированных веток (streams) сервер проверяет допустимое направление интеграции. Если изменения источника лежат за пределами view, слияние может вернуть `conflict` с `details.reason = "outside_view"`. Расширьте view до затронутых путей либо используйте полную рабочую копию целевой ветки и повторите слияние.

После `merge`, `switch`, `update` или `unshelve` проверьте конфликты. Локальный MCP-инструмент `conflicts` с путём показывает стороны конфликта. Для текста сравните базу, локальный и входящий варианты, отредактируйте файл и вызовите `lode resolve PATH --merged`. Для бинарного файла выберите содержательно верную сторону (`--mine` или `--theirs`) и проверьте файл в редакторе. Укажите выбор в описании полки. Незавершённое слияние отправляется целиком, чтобы сохранилось поле `merged_from`.

## 6. Удалённое предложение и ревью

Без рабочей копии запросите дерево через `list_dir`, прочитайте файл через `read_file` на выбранной ревизии. Проверьте признак усечения большого ответа. Передайте в `create_shelf` исходную `base_rev` и новые полные версии изменяемых файлов. Для доработки используйте `update_shelf`. Состав полки, diff и состояние checks можно запросить отдельно. Серверный MCP не запускает локальную рабочую копию или её скрипты.

Для полки с условным идентификатором 17 и версией 2:

```sh
lode --json shelf show 17
lode --json shelf diff 17
lode --json checks 17@2
```

Убедитесь, что просмотрели версию 2 и её проверки. Если задача включает принятие и у исполнителя есть права, команда `lode --json shelf submit 17@2` принимает именно просмотренную версию. При конфликте версий прочитайте актуальный diff и checks новой версии и проведите ревью снова. Для обычной задачи агента результатом служат полка и сведения для принимающего. Состояния checks включают `pending`, `success`, `failure`, `error` и `cancelled`. Пустой список не доказывает успешного прогона.

## 7. Машинные ответы и восстановление

CLI с `--json` пишет в stdout один JSON-документ. На успехе читайте `ok` и поля операции, на отказе — `error.code`, `error.details` и код выхода. Диагностические сообщения могут идти в stderr. Для больших списков путей поддерживаемые команды принимают UTF-8-файл через `--paths-from FILE`, один путь на строку. Пустой список отклоняется. [Контракт CLI и коды выхода](../lode/docs/CLI-JSON.md).

| Сигнал | Действие агента |
| --- | --- |
| `out_of_date`, `conflicted` | Сверить ревизии, получить изменения, разрешить конфликт и повторить проверку содержимого |
| `locked`, `lock_required` | Узнать владельца, получить нужную блокировку или передать вопрос владельцу |
| `permission_denied` | Сверить личность, scopes и ACL. При отсутствии прямой записи передать полку, если разрешено |
| `shelf_required`, `checks_required` | Создать полку либо прочитать проверки указанной версии и дождаться обязательных результатов |
| `validation_failed`, `validation_untrusted`, `python_missing` | Разобрать результаты, доверие или интерпретатор по [руководству по скриптам](agent-validation.ru.md) |
| `network`, ответ потерян при записи | Сначала сверить историю, статус и свои полки. При повторе commit или submit учитывать `replayed` в ответе |
| `module_disabled` | Установить, какой модуль нужен. Если это обязательная проверка, указать ограничение оператору |

Если включён feed, вызовите `wait_for_events` без `after` для начального курсора, затем передавайте полученное `next` как `after`. В удалённом MCP укажите депо. Событие содержит идентификаторы. Подробности читайте отдельным запросом. При `truncated: true` перечитайте историю и актуальные состояния полок и checks.

## 8. Desk, Unreal и сервер

**Desk.** Нативный клиент использует операции `lode-ops` и общие с CLI данные входа. Для разбора проблемы воспроизведите ту же операцию CLI в той же рабочей копии и сравните идентичность, view и версию ядра. У Desk собственные версия, сборка и закреплённая ревизия ядра. При отказе доверия владелец может проверить скрипты и настроить доверие через CLI. [Руководство Desk](../desk/docs/guide.md) · [Зависимость Desk от ядра](../desk/README.md).

**Unreal.** Плагин вызывает установленный `lode` и читает его JSON. Для диагностики зафиксируйте путь и версию этого CLI, корень рабочей копии и состояние файла. Повторите чтение статуса тем же CLI. После изменения бинарного ассета проверьте блокировку и результат в редакторе. [Руководство плагина](../unreal/docs/guide.md) · [Диагностика](../unreal/docs/troubleshooting.md).

**Сервер.** В `loded.toml` задаются хранилище, метаданные, модули и резервное копирование. Начальная диагностика на машине сервера — `loded doctor --config FILE --json`. При восстановлении проверьте используемый backend: локальная копия каталога сама по себе не охватывает внешнюю БД и внешнее объектное хранилище. Восстанавливайте в отдельное место и проверяйте чтение ревизии и её файлов до переключения клиентов. При обновлении опирайтесь на процедуру именно для развёрнутой версии и конфигурации. [Развёртывание для агентов](../lode/docs/deploy-linux-for-agents.md) · [Обновление сервера](../lode/docs/UPGRADING.md) · [Эксплуатация и защита](../lode/docs/HARDENING.md).

## 9. Если задача меняет сам Lode

Git-репозиторий исходников и пользовательское депо Lode имеют разные процедуры приёмки. При разработке начните с [правил репозитория](../AGENTS.md), [спецификации ядра](../lode/docs/SPEC.md), [архитектуры](../lode/docs/ARCHITECTURE.md) и [задач](../lode/docs/tasks/README.md). Найдите критерии приёмки, зависимости задачи и правила нужного подпроекта.

| Что вы меняли | Где и как проверить |
| --- | --- |
| Ядро, CLI или MCP | В `lode/` выполнить `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` |
| Desk, включая переход на новое ядро | В `desk/` закрепить все шесть зависимостей на одной ревизии при обновлении ядра, обновить lockfile. Выполнить `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked` |
| Плагин Unreal | Выполнить сборку и автоматические проверки соответствующей версии движка по [спецификации плагина, §9](../unreal/docs/SPEC.md) |

В отчёте по работе в депо укажите депо, ветку, исходную ревизию, изменённые пути, полку с версией либо итоговую ревизию, фактически выполненные проверки и нерешённые конфликты. В отчёте по исходникам укажите коммит или PR и результаты проверок нужного подпроекта. Различайте успешный прогон, пропуск и проверку, которая ещё выполняется.
