# M19 — Content validation

Teams want to stop invalid content (a broken JSON table, a texture with the wrong size, an
asset named against the convention) before it lands, with the rules kept in the depot so
every workspace gets them through `lode update`. This milestone adds validation scripts in
Python, kept in the depot, listed in `.lodeconfig`, run by the client before shelve and
commit, and run again by the server on every shelf version as a check that the submit gate
can require. It also adds the missing branch setting that makes a branch accept shelf submits
only, so that a direct commit cannot get around the gate. (M16 and M18, now on `main`, use
T160–T166 and T190–T194; M17 is in flight with T170–T181.)

Checked against `main` (3a855e8); re-checked after M16 and M18 merged (4d0cef5).

Ground rules for every task in this milestone:

- **The server is the enforcement, the client is fast feedback.** Anyone can skip or edit a
  check on their own computer; the server runs the scripts from the branch head, never from
  the change being checked, so a shelf cannot weaken the rule it must pass (the same rule as
  `[checks]` today, ARCHITECTURE §9.5).
- **No new concepts on the server side.** A server-side run is a check named
  `validate/<name>`, reported through `lode-mod-checks::report_check`, listed by
  `lode checks`, the MCP tool `list_checks` and Lode Desk's checks view, and enforced by the
  existing submit gate.
- **Python only, standard library first.** Lode runs `python` with arguments, never through a
  shell, and behaves the same on Windows and Linux. Installing packages a script imports is
  the team's job (documented), not Lode's.
- **Off until asked for.** A depot without `[validate]` runs nothing. The server module is off
  by default, like `webhooks` and `checks`.

## Why

| Gap | On `main` | Task |
| --- | --- | --- |
| Direct commits skip the gate | The checks gate fires only when `CommitCtx.origin` is `Module { "shelves", … }`; ARCHITECTURE §9.5 says "Direct commits are not gated … a separate feature, not in this version". A per-branch `deny write` rule blocks direct commits but also self-submitted shelves and locks (both need `write`), so it is not a substitute. | T200 |
| No place for validation rules | `.lodeconfig` knows `[locks]`, `[files]`, `[checks]`; other tables land in `LodeConfig::sections`. | T201 |
| Nothing runs on the client before shelve or commit | `lode-ops` `commit` and `shelve` go straight to the server. The `lode` command, Lode Desk and `lode mcp` all commit through `lode-ops`, so one runner covers all three. | T202, T203, T204 |
| Nothing on the server can run a check | Modules have background workers, `on_event`, read access to trees and blobs (`ModuleCtx`), and `report_check` is a public function of `lode-mod-checks`. `pre_commit` must stay fast (no network, no blob I/O), so the run cannot happen inside the commit. | T205 |
| No example a team can copy | — | T206 |

## Configuration (as it will look)

```toml
# .lodeconfig on the branch
[branches]
shelf_only = ["main", "release/*"]          # T200: direct commits refused here

[validate]
python   = "3.10"                           # minimum version; older or missing Python is reported
support  = ["tools/validate/**"]            # files a script may import or read, besides its own

[[validate.script]]
name    = "json"                            # check name becomes validate/json
run     = "tools/validate/json_valid.py"    # depot path of the script
paths   = ["Data/**/*.json"]                # runs only when a matching file changes
timeout = "60s"                             # default 60 s, at most 10 min

[[validate.script]]
name    = "naming"
run     = "tools/validate/asset_names.py"
paths   = ["Content/**"]
server  = false                             # client-only (default true)

[checks]
branches = ["main", "release/*"]            # every server-side script is required here (T205)
```

## The script contract (T202 defines it, T205 reuses it)

- Started as `<python> -X utf8 <script>` with the working directory at a root that holds the
  depot's files at their depot paths (the workspace on a client, a temporary tree on the
  server). Environment: `PYTHONDONTWRITEBYTECODE=1`, `PYTHONUTF8=1`, `LODE_VALIDATE=1`; no
  `LODE_TOKEN*`, no proxy settings.
- Standard input is one JSON document:
  `{ "version": 1, "phase": "shelve" | "commit" | "manual" | "server", "depot", "branch",
     "files": [ { "path", "action": "add" | "edit" | "delete" | "move", "from"? } ] }`.
  Only files matching the script's `paths` are listed; deleted files are listed but absent on
  disk. A script whose list would be empty is not started.
- Exit code 0 passes, 1 fails, anything else (or a timeout) is an error. An error counts as a
  failure for the gate, and is shown as "the check itself broke", not as bad content.
- Standard output: zero or more JSON lines
  `{ "path"?, "line"?, "level": "error" | "warning", "message" }`; any line that is not such
  JSON is kept as plain text. Output is cut at 64 KiB and says so. Standard error is kept as
  plain text for the "check broke" case.

## T200 — Branches that accept shelf submits only

**Goal:** a branch can require every change to come through a shelf, so the checks gate
cannot be bypassed by a direct commit.
**Depends on:** —.
**Scope:** `lode-core` (config), `lode-server` (commit engine), `lode-ops`, `lode-desk`,
docs.

**Requirements**
- `.lodeconfig` `[branches] shelf_only = [GLOB, …]`, parsed in `lode-core` like
  `[checks].branches`; a bad glob makes the file invalid (`invalid_request`, as today).
- In the commit engine, read from the branch head configuration: a commit to a matching
  branch whose origin is not `Module { "shelves", … }` is refused with the new code
  `shelf_required`, `details: { branch }`. This covers `lode commit`, a `lode merge` result,
  MCP `commit` and the HTTP API. Branch creation is not a commit and is unaffected.
- Escape hatch, in the same style as M16's `EXT_FORCE_FLOW`: a depot admin may commit
  directly with `lode commit --override "<reason>"` (commit extension `override_shelf_only`
  with the reason); the revision records `override = { by, reason }`, which `lode log`, the
  admin web UI and Lode Desk history show. Everyone else, agents included, gets
  `permission_denied`.
- With the shelves module off, a `shelf_only` branch refuses every commit except overrides;
  the server warns about this at start and on `lode admin` depot views.
- `lode-ops`, Lode Desk and `lode mcp` turn `shelf_required` into "This branch takes
  changes through shelves only. Shelve your changes and submit the shelf." Lode Desk offers
  "Shelve instead" with the same files and description.
- SPEC §5.6 and §6.6, ARCHITECTURE §9.5 (remove "Direct commits are not gated"), CLI-JSON
  (`shelf_required`, `override`), user guide.

**Acceptance**
- Server tests: a direct commit to `main` with `shelf_only = ["main"]` is refused; a shelf
  submit to it passes; a commit to `dev` passes; an admin override lands and records the
  reason; an agent with `write` cannot override; a non-admin override is `permission_denied`; a merge result committed directly is
  refused, the same merge shelved and submitted is accepted.
- A shelf that changes `shelf_only` itself is judged by the head rule, not its own.
- CLI test: exit 1, code `shelf_required`, readable message.

**Out of scope:** per-path rules; required reviewers.

## T201 — `[validate]` in `.lodeconfig`

**Goal:** server and client read the same validation rules from the branch head.
**Depends on:** —.
**Scope:** `lode-core` (`config.rs`), docs.

**Requirements**
- Parse `[validate]` (`python`, `support`) and `[[validate.script]]` (`name`, `run`,
  `paths`, `timeout`, `server`) into `LodeConfig::validate`. Unknown keys are ignored, as for
  the rest of the file.
- Invalid (refused at commit, as today): a `name` that is not a valid check name after the
  `validate/` prefix, duplicate names, `run` that is not a valid depot path or does not end in
  `.py`, a bad glob, `timeout` outside 1 s to 10 min, a `python` that is not `3.N` or
  `3.N.M`.
- A commit that adds a script entry whose `run` file does not exist in the resulting tree is
  refused with `invalid_request`, so a typo never reaches the client.
- SPEC §5.6 gains the section; the user guide gains a short "Validation scripts" page that
  T206 fills.

**Acceptance**
- `lode-core` unit tests for every rule above; server test for the missing-script refusal.

**Out of scope:** running anything.

## T202 — Run validation in `lode-ops` and the `lode` command

**Goal:** `lode shelve` and `lode commit` run the depot's scripts first and stop on failure.
**Depends on:** T201.
**Scope:** `lode-ops` (new `validate` module), `lode-cli`, docs.

**Requirements**
- **Finding Python**, in order: `LODE_PYTHON`; `python` in the user's `settings.toml`; on
  Windows `py -3`, then `python`; elsewhere `python3`, then `python`. The version is read once
  per run with `-c "import sys; print(*sys.version_info[:3])"`. Missing or older than
  `[validate].python`: the message names the version needed and both ways to point Lode at
  one. Default is to warn and go on, since the server checks again; `settings.toml`
  `validate_missing_python = "refuse"` makes it a refusal.
- **Running:** the contract above, from the workspace root, for each script whose `paths`
  match the files being shelved or committed (changelist-aware: only that changelist's
  files). Scripts run one at a time in `.lodeconfig` order; all of them run even after a
  failure, so the person sees every problem at once. The scripts used are the workspace's
  copies (local edits included); the rule list is the workspace branch head's `.lodeconfig`,
  as for locks.
- **Commands:** `lode shelve` and `lode commit` run validation unless `--no-verify` is given;
  `lode validate [PATH…] [--changelist N] [--script NAME]` runs it on demand. Refusal: exit 1,
  code `validation_failed`, `details: { results: [ { name, outcome: "passed" | "failed" |
  "error" | "skipped", problems: [ { path?, line?, level, message } ], text?, seconds } ] }`.
  Warnings alone do not refuse. Human output groups problems by file.
- **Trust before running.** Running a script from the depot runs code on the person's
  computer, and M16 kept merge tool commands out of the depot for that reason. So the first
  time a workspace would run a script, or after the script's content changes, `lode` asks
  once: "This depot wants to run tools/validate/json_valid.py before shelve and commit. Run
  it?" (`--json` and non-interactive runs refuse with `validation_untrusted` instead). The
  answer is kept per depot and script content hash in `settings.toml`;
  `lode validate --trust` and `settings.toml` `validate_trust = ["<server>/<depot>"]` trust a
  depot for unattended machines and agents.
- Progress on standard error: "Checking json (3 files)…".
- CLI-JSON, SPEC §9, user guide.

**Acceptance**
- Tests in `lode-cli/tests/validate.rs`, run on the Windows and Linux CI jobs (both runners
  have Python 3; the job fails if it is missing rather than skipping): pass, fail with JSON
  lines, plain-text output, exit code 2 is `error`, timeout, a script whose paths do not match
  is not started, deleted files listed but absent, `--no-verify`, missing Python warns by
  default and refuses with the setting, an untrusted script is not run and a changed script
  asks again, a script that imports a `support` file works.
- No shell is involved: a file name with spaces, quotes and `&` reaches the script intact.

**Out of scope:** installing Python or packages; running scripts in parallel.

## T203 — Validation through `lode mcp`

**Goal:** an agent gets the same refusal a person does, and can run the checks itself.
**Depends on:** T202.
**Scope:** `lode-cli` (`src/cmd/mcp.rs`), docs.

**Requirements**
- `shelve` and `commit` run validation; a refusal is the tool error `validation_failed` with
  the same `details` as T202. There is no way to skip it from MCP.
- New tool `validate { paths?: [string], changelist?: int, script?: string }`, listed for
  every token that can read, answering the T202 JSON.
- Tool descriptions say to call `validate` before `shelve` when content rules exist.
- MCP.md gains "Validation".

**Acceptance**
- `lode-cli/tests/mcp.rs`: refused shelve with problems, passing shelve, `validate` tool.

## T204 — Validation in Lode Desk

**Goal:** a person sees what is wrong, file by file, before anything is sent.
**Depends on:** T202 (T200 for "Shelve instead").
**Scope:** `lode-desk`, `docs/desk-guide.md`.

**Requirements**
- Commit and Shelve run validation first, with "Checking json (3 files)…" in the commit
  panel and a Cancel button that stops the running script.
- On failure, a results panel replaces the commit panel: one row per script with its outcome,
  problems grouped by file with line numbers; clicking a problem selects the file in the
  changes list and opens its diff at that line. "Check broke" shows the script's text output.
- Buttons: "Fix and check again"; "Shelve anyway" (the server will check again, and the shelf
  cannot be submitted to a gated branch until it passes); "Commit anyway" only on branches
  that are not `shelf_only`. Both "anyway" actions are one click, never the default button.
- A "Check changes" button on the changes view runs `lode validate` on the selection.
- The trust question from T202 is a dialog naming the script, with "Show script" and
  "Run" / "Don't run".
- Missing Python shows once per session as a banner with a link to the help page.
- Screenshots for the desk guide, light and dark.

**Acceptance**
- `lode-desk/tests`: results model from a refused run, click-to-file mapping, "anyway"
  paths, cancel stops the child process (Windows and Linux).

## T205 — Server-side validation module

**Goal:** the server runs the branch's scripts on every shelf version and reports the result
as checks, so the existing gate enforces them.
**Depends on:** T201; T200 recommended before anyone relies on it.
**Scope:** new crate `lode-mod-validate`, `lode-mod-checks` (implicit requirements),
`loded` (config), docs.

**Requirements**
- Module `validate`, off by default (`[modules] validate = true`); it needs `checks` and
  `shelves` on and refuses to start otherwise, naming both.
- `loded.toml` `[validate]`: `python` (path; required when the module is on, checked at
  start), `workers` (default 2), `max_input_mib` (default 512 per run), `work_dir` (default
  `<data>/validate`).
- On `shelf.created` and `shelf.updated`, queue a run in the module's own table (keyed by
  depot, shelf, version) and report every applicable `validate/<name>` as `pending`. A worker
  then builds a temporary tree: the shelf's changed files that match any script's `paths`,
  plus `support` files and the scripts themselves **from the target branch head**, and runs
  each script with `phase: "server"`. Results are reported as `success` or `failure` with
  the first problems as summary (1 KiB) and the rest in the module's own table, served at
  `GET /depots/{d}/validate/{shelf}/{version}` (scope `read`) and linked by the check's `url`.
- Reporter: a service user `lode-validate`, created at first start, that cannot sign in and
  holds only the `checks` scope.
- Implicit requirement: on branches in `[checks].branches`, every `[[validate.script]]` with
  `server = true` is required as `{ name = "validate/<name>", reporter = "lode-validate" }`
  without listing it in `[checks].required`. The gate keeps reading the rule from the branch
  head.
- A new shelf version supersedes a queued or running run for the older version (the child is
  stopped). Runs survive a server restart (queued rows are picked up again).
- Safety, documented in HARDENING.md: scripts come only from branch heads, so changing what
  the server runs takes a submitted shelf; the child runs as the `loded` user in a fresh
  directory, with a cleared environment, the script's timeout and a cap on output. This is
  not a sandbox: anyone who can land a script on a gated branch can run code on the server.
  The guide recommends running `loded` as its own user or in the container image, which
  gains Python 3.
- Admin web UI: the module's queue and last runs on the depot page.
- SPEC §6 (new "Validation" section), ARCHITECTURE §9 (new module), UPGRADING, admin guide.

**Acceptance**
- `lode-mod-validate/tests`: a passing and a failing shelf; submit refused with
  `checks_required` naming `validate/json` while pending and after failure, accepted after a
  fixed version passes; a shelf that edits the script itself is still checked by the head
  version; supersede on a new version; restart resumes a queued run; a script that times out
  reports failure with "check broke"; module refuses to start without `checks`. Also with
  Postgres (`LODE_TEST_POSTGRES`).

**Out of scope:** validating direct commits on branches that are not `shelf_only` (use
T200); running anything other than Python; sandboxing beyond the above.

## T206 — Example scripts, guide and end-to-end test

**Goal:** a team can copy a working setup in ten minutes.
**Depends on:** T202–T205.
**Scope:** `examples/validate/`, docs, `lode-testkit`.

**Requirements**
- `examples/validate/`: `json_valid.py` (every changed JSON file parses), `asset_names.py`
  (names match a pattern from a small TOML file in `support`), and `max_size.py` (files under
  a size limit), standard library only, each under 80 lines, with the `.lodeconfig` above.

## Decisions for review

1. Server-side results are checks named `validate/<name>`, reported by the service user
   `lode-validate`, rather than a separate gate. Visible everywhere checks are already shown.
2. Every server-side script is required on `[checks].branches` automatically, so the two lists
   cannot drift. Alternative: list them in `[checks].required` by hand.
3. Missing Python on a client warns and goes on by default (the server catches it).
   Alternative: refuse by default.
4. Depot admins can override `shelf_only` with a recorded reason, as with M16's stream rules,, so a broken check can
   never lock a branch. Alternative: no override at all.
5. Scripts from the depot run on people's computers only after a one-time trust prompt per
   script version (T202). Alternative: trust any depot the person has checked out.
6. Client-side direct commits on branches that are not `shelf_only` are validated only by
   the client.
