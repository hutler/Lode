# M3 — Locks, shelves, changelists

Module crates may use only `ModuleCtx` and the `Module` trait (AGENTS.md). If something is
missing from that surface, extend the surface in `lode-server` in the same pull request and say
so in the report.

## T030 — Locks module, server (`lode-mod-locks`)

**Goal:** exclusive locks enforced at commit time.
**Depends on:** T017.

**Requirements**
- Table, endpoints, `pre_commit` and `in_commit` behaviour exactly per ARCHITECTURE §9.1 and
  SPEC §6.1. Add request/response types to `lode-proto`.
- `[locks].required` is taken from the branch configuration in `CommitCtx` (the core parses
  the head `.lodeconfig`, T014); the module does no blob I/O. Lock ownership is judged against
  the commit's author, not its submitter. A commit that itself changes `.lodeconfig`
  is checked against the old version.
- Locking a path that does not exist at head → `not_found`. Locking is idempotent for the
  same owner and workspace; a different workspace of the same owner → `locked`.
- Emits `lock.acquired` / `lock.released` outbox events.
- Contributes the MCP tool `list_locks` through `mcp_tools()` (scope `read`).
- Declares the scope `lock` through `Module::scopes()` as an agent default. Event payloads
  per ARCHITECTURE §8.1 (no paths).

**Acceptance**
- Lock, list, unlock; second principal gets `locked` with holder details.
- All-or-nothing: one unavailable path means none are taken.
- Stale `base_id` → `out_of_date`.
- Commit by non-holder → `locked`; commit of a lock-required file without lock →
  `lock_required`; adds are exempt; holder's commit succeeds and releases unless `locks.keep`.
- Force-unlock requires admin.
- With the module disabled, the endpoints are absent and commits ignore `[locks]`.

**Out of scope:** cross-branch locks, client behaviour.

## T031 — Locks, client

**Goal:** lock commands and read-only enforcement in the workspace.
**Depends on:** T030, T025.
**Scope:** `lode-client`, `lode-workspace`, `lode-cli`.

**Requirements**
- `lode lock <path>… [-m comment]`, `lode unlock <path>… [--force]`, `lode locks [--mine]
  [path-prefix]`; `commit --keep-locks`.
- `lock` refuses files that are locally out of date and tells the user to update first.
- Files matching `[locks].required` are set read-only on disk after checkout/update/commit/
  unlock and writable after `lock` (Windows read-only attribute; Unix write bits). `status`
  flags lock-required files that were modified without a lock.
- `status` shows locks held; `lock_held` in the workspace database is reconciled with the
  server on `update` and `locks`.
- Commands degrade with a clear message when the server reports the module is not enabled.

**Acceptance**
- End-to-end: user A locks, user B's commit is refused, A commits, lock released, B updates
  and can lock.
- Read-only bit transitions verified on each platform.
- A lock broken by an admin is noticed at the next `update`.

**Out of scope:** GUI or editor integration.

## T032 — Shelves module, server (`lode-mod-shelves`)

**Goal:** server-stored change sets.
**Depends on:** T017.

**Requirements**
- Tables, create/replace/list/get/delete endpoints and `gc_roots` per ARCHITECTURE §9.2.
  Add types to `lode-proto`.
- Create validates the change set like a commit would (paths, blob existence, `base_id`
  matches the file at `base_rev`, read permission on the base paths) but does not need `write`
  permission on the paths; needs scope `shelve`.
- Shelves are readable by anyone with `read` on all of the shelf's paths; otherwise the shelf
  is hidden.
- `GET …/{id}?diff=true` adds, per text file, a unified diff against the base (size-capped).
- Emits `shelf.created|updated|deleted` events.
- `version` starts at 1 and rises by one on every `PUT`; it is returned in every shelf
  response. `PUT` may change `base_rev`; each change's `base_id` is validated against the new
  base. Create and `PUT` accept an optional `merged_from`, validated as in a commit.
- Shelf responses include the owner's `kind` and, for agents, `owner`.
- Contributes the MCP tools `list_shelves` and `get_shelf` through `mcp_tools()` (scope `read`).
- Declares the scope `shelve` through `Module::scopes()` as an agent default. Event payloads
  per ARCHITECTURE §8.1 (no paths).

**Additional acceptance**
- Version increments on `PUT` and not on reads; a `PUT` with a new `base_rev` succeeds when
  the changes match the new base and fails `out_of_date` otherwise.

**Acceptance**
- Create, replace, list with filters, delete (owner and admin; others refused).
- Shelf blobs survive GC while open and are collected after deletion plus grace period.
- A shelf touching a path the reader cannot read is not listed for that reader.
- Invalid `base_id` → `out_of_date`; missing blob → `missing_objects`.

**Out of scope:** submit (T035), client.

## T033 — Shelves, client

**Goal:** shelve and unshelve from a workspace.
**Depends on:** T032, T025.
**Scope:** `lode-client`, `lode-workspace`, `lode-cli`.

**Requirements**
- `lode shelve -m DESC [paths…] [--keep] [--update <id>]`, `lode shelves [--mine] [--user U]`,
  `lode shelf show <id>`, `lode shelf diff <id>`, `lode unshelve <id>`, `lode shelf delete <id>`.
- `shelve` uploads like a commit, then reverts the shelved files unless `--keep`.
- `shelf show`, `shelf diff` and `shelves` print the shelf's version. Reading shelves needs
  only scope `read`.
- When T051 is merged, `shelve` during a pending merge sends the pending `merged_from` and
  `unshelve` restores it; until then leave a tracked follow-up in the report.
- `unshelve` applies the shelf's changes on top of the workspace with the same merge and
  conflict handling as `update` (base = shelf base content, theirs = shelf content). Works for
  shelves of other users.

**Acceptance**
- Shelve → workspace clean → unshelve restores the exact pending state (content, adds,
  deletes, renames).
- Unshelve of another user's shelf onto a workspace with overlapping local edits merges or
  conflicts correctly.
- `--update` replaces the shelf's contents.

**Out of scope:** review workflow, comments.

## T034 — Changelists

**Goal:** named local groups of pending changes.
**Depends on:** T024.
**Scope:** `lode-workspace`, `lode-cli`.

**Requirements**
- `lode changelist new <name> [-m desc]`, `list`, `move <name> <paths…>`, `delete <name>`
  (files return to `default`); `status` groups by changelist; `commit -c <name>` uses the
  changelist's files and its description as the default message; `add/rm/mv` accept `-c`.
- A committed or reverted file leaves its changelist; an empty non-default changelist is
  deleted after commit.
- `shelve -c` is wired here if T033 is merged; otherwise leave a tracked follow-up in the
  report.

**Acceptance**
- Two changelists with disjoint files commit as two revisions with the right contents.
- Moving a file between changelists and deleting a changelist behave as specified.

**Out of scope:** server-side pending changelists.

## T035 — Shelf submit

**Goal:** commit a shelf on the server; the approval path for agent work.
**Depends on:** T033.
**Scope:** `lode-mod-shelves`, `lode-cli`.

**Requirements**
- `POST …/shelves/{id}/submit` per ARCHITECTURE §9.2, using `Commits` with an author override
  (extend `ModuleCtx` only if the override is not already exposed). Optional body
  `{message}`; default message is the shelf description. Provenance of the revision is the
  shelf's provenance plus `submitted_shelf: <id>`; `rev_meta` gets `shelves.shelf_id`.
- Idempotent: submitting an already submitted shelf returns its revision.
- The commit is made with `origin = Module { "shelves", { shelf_id, shelf_version } }`
  (ARCHITECTURE §8), and `shelf.submitted` is written in the commit transaction.
- The request must carry `expected_version`; if it is not the shelf's current version the
  submit fails `conflict` and reports the current version. The shelf's `merged_from` is passed
  to the commit.
- `lode shelf submit <id>[@<version>] [-m MSG]`. With a version, that version is submitted.
  Without one, on an interactive terminal the CLI shows the shelf (owner, version, files) and
  asks for confirmation, then submits the version it showed; when not interactive or with
  `--json`, the version is required (usage error otherwise).

**Acceptance**
- Submitted revision has author = shelf owner and submitter = caller; contents equal the shelf.
- Branch moved under the shelf on a touched file → `out_of_date`, shelf stays open.
- Caller without `write` on a path → `permission_denied`.
- Shelf updated between review and submit: a submit naming the old version fails `conflict`
  and commits nothing.
- A shelf carrying `merged_from` produces a revision with the same merge record.
- Locks module interaction: a shelf touching a path locked by a third party is refused; a
  lock held by the shelf owner satisfies `lock_required`.

**Out of scope:** automatic rebase of shelves.
