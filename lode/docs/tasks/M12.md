# M12 — Lode 0.2: obliterate, SVN import, single sign-on, S3 storage

Group 1 of the v2 candidates in the plan "Lode after v1" (2026-11-14): the four features a
team is most likely to ask for once it runs Lode for real. Each one is independent of the
others; obliterate goes first because without it the first committed secret cannot be
removed from a depot. The milestone ends with release 0.2.0.

## T120 — Obliterate

**Goal:** permanently remove a file's content from a depot, such as a leaked password or a
40 GB asset committed by mistake.
**Depends on:** T019, T053.
**Scope:** `lode-core`, `lode-proto`, `lode-meta`, `lode-server`, `lode-client`, `lode-ops`,
`lode-cli`, `lode-desk` (error text only), docs.

**Requirements**
- Obliterate removes **content**, not history. Revisions, their messages and the paths they
  changed stay; trees keep naming the content's id, so every tree id and every revision stays
  valid. The stored objects are deleted, and the depot records each obliterated id with its
  size, the reason, who did it and when.
- `POST /admin/depots/{d}/obliterate` (server admin): select by path, every version of a file
  (or of every file under a folder) on every branch, or by `PATH@REV`, the version a revision
  had. The answer lists each object with its size and every revision and path that used it,
  including other paths with the same content. `dry_run` answers without changing anything.
- Refused while an active branch's head still holds the content (`conflict`, with the
  branches and paths in `details`): commit the deletion or a fixed file first. Archived
  branches and older revisions are history and do not block. The empty file cannot be
  obliterated.
- Commits cannot interleave: the check, the record and the deletion run under the GC fence.
- Afterwards the content cannot come back: uploading it again is refused with the new error
  code `obliterated` (HTTP 410), and so is downloading it, reading it through `cat`, MCP or a
  manifest, and blaming a version that is gone (blame stops at the newest obliterated version
  and says the result is truncated).
- Checkout, update, switch and view changes place everything else and leave out obliterated
  files, listing them in the result (`obliterated` in `--json`) with a warning.
- `GET /admin/depots/{d}/obliterated` lists what was obliterated.
- GC deletes an obliterated object that is still stored (for instance after a crash between
  the record and the deletion); fsck reports one as a problem. A referenced object that is
  missing because it was obliterated is not a problem.
- CLI: `lode admin obliterate <depot> <path[@rev]>… --reason TEXT [--dry-run] [--yes]` asks
  for confirmation after showing the dry run, and `lode admin obliterated <depot>` lists.
- Docs: SPEC (§5.8 and the error code), ARCHITECTURE §11, CLI-JSON, the user guide's admin
  chapter (what obliterate does not reach: existing backups, workspaces and shared caches on
  people's computers, and webhooks already delivered), the Desk guide's error list.

**Acceptance**
- A file committed with a secret, then fixed: obliterating it removes the object, `cat` of the
  old revision and download of the id answer `obliterated`, uploading the same content is
  refused, and `log` still lists the revisions.
- Obliterating content still in an active head is refused with the branch and path; the same
  content only on an archived branch is allowed.
- Dry run changes nothing and lists every use, including a copy at another path.
- A checkout of an old revision places every other file and reports the obliterated one; a
  later update past the fix works.
- Blame of a file whose older version is obliterated stops there and is marked truncated.
- GC removes a still-stored obliterated object; fsck reports it before GC and is clean after;
  fsck is clean for revisions that reference obliterated content.
- A non-admin is refused.

**Out of scope:** rewriting history (removing revisions or paths), obliterating tree
objects, reaching into backups.

## T121 — SVN importer

**Goal:** move a project from Subversion to Lode with its history.
**Depends on:** T086.
**Scope:** `lode-import`, `lode-ops`, `lode-cli`, docs.

**Requirements**
- `lode import svn <url> <server-url>/<depot>` replays the revisions that change one
  directory of a Subversion repository (the URL names it, usually the trunk) onto `main`, one
  Lode revision per SVN revision, like the Git importer: the message, and provenance `imported`
  with system `svn`, the revision number, author and date.
- Runs the `svn` command (no library), with `svn log --xml -v` for the history and `svn cat`
  / `svn export` for content. Works with `file://`, `svn://`, `http(s)://` URLs and the
  credentials `svn` already has.
- Copies inside the imported path become Lode copies or renames (a copy plus a delete in the
  same revision). A copy from outside the path is an add. `svn:executable` sets the executable
  bit; `svn:special` links become symlinks; `svn:externals` are skipped and counted.
- Resumable and safe to repeat, through the branch head's provenance and request ids
  `import-svn-<rev>`, exactly as the Git importer.

**Acceptance**
- A test repository made with `svnadmin` and `svn` (adds, edits, deletes, a rename, an
  executable, a symlink, an external, a revision outside the path) imports with the right
  contents per revision; an interrupted import resumes. Skipped where `svn` is not installed.

**Out of scope:** importing SVN branches and tags as Lode branches; `svn:mergeinfo`.

## T122 — Single sign-on (OIDC)

**Goal:** sign in through the company's identity provider (Google, Microsoft Entra, Okta,
Keycloak) instead of a Lode password.
**Depends on:** T040.
**Scope:** `lode-server`, `loded`, `lode-client`, `lode-ops`, `lode-cli`, `lode-desk`, docs.

**Requirements**
- `[oidc]` in `loded.toml`: `issuer`, `client_id`, `client_secret` (or `client_secret_file`),
  `scopes`, the claim that names the user (`email` by default), `allowed_domains`, and
  `auto_create` (create a user on first sign-in, default off: an admin adds users first).
- The server is the OIDC client (authorization code with PKCE). It reads the issuer's discovery
  document and keys, checks the ID token's signature (RS256 and ES256), issuer, audience,
  expiry and nonce, and issues an ordinary Lode token with the default scopes.
- `lode login URL --sso` opens the browser and waits on a loopback address for the server to
  hand the token back; `--no-browser` prints the link instead. Lode Desk's sign-in dialog gets
  "Sign in with SSO" when the server offers it (`GET /info` names it).
- Password sign-in can be turned off for everyone but server admins.
- Disabled Lode users stay refused, whatever the provider says.

**Acceptance**
- Against an in-process test provider (its own keys, discovery and token endpoint): a full
  sign-in issues a token; a wrong audience, an expired token, a bad signature, a reused nonce
  and a domain not allowed are each refused; `auto_create` off refuses an unknown user.
- The CLI's loopback receives the token (driven by the test instead of a browser).

**Out of scope:** SAML; group sync from the provider; SCIM.

## T123 — S3 blob storage

**Goal:** keep a depot's content in S3-compatible storage (AWS, Backblaze B2, MinIO), so a
small server can hold a large depot.
**Depends on:** T012.
**Scope:** `lode-store`, `loded`, `lode-server` (backup and GC), docs.

**Requirements**
- `[storage] kind = "s3"` with `bucket`, `prefix`, `region`, `endpoint` (for non-AWS),
  `path_style`, and credentials from `access_key_id`/`secret_access_key_file` or the usual
  `AWS_*` environment variables.
- `S3BlobStore` implements `BlobStore`: objects keep the stored format of ARCHITECTURE §3.3
  under `<prefix>/<depot-id>/<h0h1>/<h2h3>/<id>`; uploads go to a local temporary file first
  (hash checked, compressed) and then to S3 with a conditional put (`If-None-Match: *`) so an
  object is never replaced; reads stream; `list` pages through ListObjectsV2.
- Requests are signed with AWS Signature Version 4 over `reqwest`, with no AWS SDK.
- GC and fsck work unchanged. `loded backup` keeps copying the database; the guide says to use
  the bucket's own versioning or replication for content.
- `loded migrate-storage --to s3` copies a filesystem depot's objects into the bucket (resumable)
  and then switches the config.

**Acceptance**
- Signature tests against the published AWS SigV4 examples.
- The store's test suite (the one the filesystem store passes) runs against an in-process
  fake S3 server, and against MinIO when `LODE_TEST_S3` points at one (CI starts MinIO).
- A full server scenario (commit, checkout, GC) on the fake S3.

**Out of scope:** multipart uploads above 5 GB (a later task with chunked storage), Azure
Blob and Google Cloud Storage.
