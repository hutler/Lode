# M17 — Field feedback from the first real deployment

On 2026-11-20 an AI agent deployed `loded` on a fresh Debian 13 VPS by following
[`docs/deploy-linux-for-agents.md`](../deploy-linux-for-agents.md), and a team then used the
admin web UI, the CLI and Lode Desk for real work (users, access rules, one depot, a
270-file / 268 MB commit, MCP). This milestone turns what they hit into tasks. (M16 is kept
for v2 group 3: streams and smarter merge.)

Ground rules for every task in this milestone:

- **Grow convenience around what exists** (shelves, locks, checks, webhooks, `lode://`
  links, the admin web UI). No new concepts: no review approvals, inline comments, CI
  runners, issue tracking, extra SSO providers or clustering.
- **Do not regress** what worked: one binary, one port, one config file, built-in
  Let's Encrypt over TLS-ALPN-01, a verification command after every runbook step, and agents
  that propose by shelf with `read,lock,shelve` and no `write`.
- Every CLI addition has `--json` output documented in [`CLI-JSON.md`](../CLI-JSON.md), and
  the user guide gains the matching section.

## T170 — Generated admin password, one secret

**Goal:** a person who cannot use SSH still gets a working admin sign-in, and setup hands out
one secret instead of two.
**Depends on:** —.
**Scope:** `loded`, `lode-server`, `lode-proto`, `lode-ops`, `lode-cli`, admin web UI, docs.

**Requirements**
- `loded setup --generate-admin-password`: a random password (20 characters from an
  unambiguous alphabet) printed once at the end. Without a terminal and without
  `--admin-password-file`, setup generates one instead of failing.
- A generated password is marked *must change*: it signs in only to set a new password, and
  stops working 24 hours after setup if unused. `loded reset-admin --generate-password`
  makes a new one offline (same rules).
- New `POST /auth/password` (name, current password, new password; rate limited like login).
  Any password user can change their own; this is also how a must-change password is
  replaced. `lode login` meets error `password_change_required`, asks for a new password
  (twice, no echo) and continues. New `lode passwd` for changing one's own password at any
  time (prompt, or `--password-stdin`). SSO-only users get `no_password`.
- The admin web sign-in sends a must-change account to a "Choose a new password" page.
- Setup no longer creates or prints an admin token. `--print-admin-token` keeps the old
  behaviour for scripts. `reset-admin` keeps printing a token (it is the recovery path).
- Runbook: the no-SSH path uses `--generate-admin-password`; the agent passes the printed
  password to the person once and says it must be changed at first sign-in. The `/root` file
  path stays for people who have SSH.

**Acceptance**
- Setup tests: generated password signs in only through the change flow; it expires after
  24 hours (test clock); no token in setup output unless `--print-admin-token`.
- `lode passwd` and the `lode login` change flow in CLI tests; wrong current password and
  rate limit refused; SSO-only user gets `no_password`.
- Admin web: a must-change sign-in lands on the change page and reaches the overview after.

**Out of scope:** password rules beyond the existing minimum length, password reset by email.

## T171 — No-domain path with sslip.io in the runbook

**Goal:** a team without a domain gets HTTPS on a public address in the same few steps.
**Depends on:** —.
**Scope:** docs, `loded` (one hint).

**Requirements**
- `deploy-linux-for-agents.md`: when the person has no domain, offer `<public-ip>.sslip.io`
  (dashes for IPv6) as the recommended path, with `--domain` set to it and the usual DNS
  check (`getent hosts`). Say plainly that it relies on a free third-party DNS service and
  suits trials; a real domain is better for a team that stays. `--local` stays for
  machine-only tests.
- User guide quick start and `loded setup`'s domain prompt mention the same option
  ("No domain? Use <ip>.sslip.io").

**Acceptance:** manual: the runbook's no-domain branch followed on a VPS gets a certificate
(the field session already did this by hand). Docs build and links check pass.

**Out of scope:** detecting the public IP automatically, bundling a DNS service.

## T172 — Filter access rules by depot

**Goal:** `lode admin acl list` stays readable on a server with many depots.
**Depends on:** —.
**Scope:** `lode-server`, `lode-proto`, `lode-client`, `lode-ops`, admin web UI.

**Requirements**
- `GET /admin/acl?depot=D` returns the rules that can apply in depot D (rules for D and
  server-wide rules), still in evaluation order. Also `?subject=NAME`.
- `lode admin acl list [--depot D] [--subject NAME]`; unknown depot is `not_found`.
- The admin Access page gets the same two filters (GET form, so the URL can be shared).

**Acceptance:** handler and CLI tests with rules across three depots, server-wide rules and
both filters; evaluation order unchanged.

## T173 — Read-only depot browser on the web

**Goal:** answer "what is inside depot X" in a browser, without a checkout.
**Depends on:** T170 (the account page uses its password change).
**Scope:** `lode-server` (web UI), docs.

**Requirements**
- Pages under `/web/` for **any signed-in user**, built on the admin UI's sessions, layout and
  escaping. Each page acts through the API in process as that user, so access rules apply
  unchanged and a depot they cannot read is `not_found`. `/admin/` stays admins-only; admins
  see a link between the two.
- Depots the user can read; a depot's branch picker; file tree at a revision (folders first,
  size, last change); a file's history; text files shown with line numbers (up to the
  existing 16 MB text limit, larger ones offered as a download); PNG, JPEG, GIF and WebP shown
  inline; other binaries as a download. A revision page lists its files with a unified text
  diff.
- Every page has "Copy `lode://` link" for what it shows (same link forms as Lode Desk).
- An "Account" page: own tokens (list, revoke) and the password change from T170.

**Acceptance:** handler tests for each page, including access refused for a depot the user
cannot read, a large text file, an image and an obliterated file (`obliterated` shown, no
content). Playwright screenshots, light, dark and phone width.

**Out of scope:** editing or committing from the web, search across file contents, blame
(can follow later).

## T174 — Shelf review on the web

**Goal:** close the "agent proposes, human submits" loop in a browser.
**Depends on:** T173.
**Scope:** `lode-server` (web UI), docs.

**Requirements**
- `/web/<depot>/shelves`: open shelves with owner (agent and its owner), description,
  version, base revision, required checks state.
- A shelf's page: files with a unified or side-by-side diff against its base, images side by
  side, the checks per version, and its `lode://` link.
- Buttons for what the API already allows, with the API's own rules: **Submit** (the commit
  description prefilled, editable; required checks and the submit gate apply, unmet checks
  listed), **Delete** with a confirmation. No new "approve" state: submitting is the
  acceptance, and checks are the gate.

**Acceptance:** handler tests: submit by a user with `write`, refused without it, refused
with unmet checks (each reason shown), stale base reported as the API reports it; delete.
An end-to-end test: an agent shelves through MCP, a user submits on the web, the revision
records `submitted_shelf`.

**Out of scope:** comments on lines, review requests, approvals.

## T175 — Chat notifications from webhooks

**Goal:** a team hears in its chat when a shelf waits for review and when locks change.
**Depends on:** T174 for the review link in messages; the rest can start any time.
**Scope:** `lode-mod-webhooks`, `lode-proto`, `lode-ops`, admin web UI, docs.

**Requirements**
- A hook gains `format`: `lode` (today's signed JSON, the default), `slack`, `discord` or
  `telegram`. The three chat formats send a one-line text in the body those services expect
  (`{"text":…}`, `{"content":…}`, `{"text":…}` with `chat_id` taken from the hook URL's
  query), naming the event, depot, who, the shelf or path, and a web link (T173/T174 page)
  when the server knows its public address.
- `lode admin webhook add --format F`; the admin Webhooks page gets a format picker.
- Docs: a recipe per service (where to get the URL, which events to pick, a test send).

**Acceptance:** delivery tests per format against a recording test server; existing `lode`
format bodies and signatures byte for byte unchanged.

**Out of scope:** email, message templates, per-user subscriptions.

## T176 — `lode link`

**Goal:** the CLI and agents can hand out the same `lode://` links Lode Desk copies.
**Depends on:** —.
**Scope:** `lode-ops` (or `lode-proto`), `lode-cli`, `lode-desk`, `lode-mod-mcp`, docs.

**Requirements**
- Move the link builder and parser from `lode-desk/src/links.rs` into a shared crate; Desk
  uses it unchanged (its shared test cases move with it).
- `lode link PATH[@REV]`, `lode link -r REV`, `lode link --shelf ID`, from the workspace's
  server and depot (`--depot` to override); prints the link, `--json` adds its parts.
- `lode shelve --json` and the MCP `create_shelf`/`update_shelf` results include the shelf's
  link, so an agent can paste it without another call.

**Acceptance:** the shared link cases pass in both crates; CLI tests for each form; MCP test
for the link in `create_shelf`.

**Depends on:** —.

## T178 — `loded doctor` and `lode doctor`

**Goal:** one command for the checks the field session did by hand.
**Depends on:** T171 (wording for sslip.io names).
**Scope:** `loded`, `lode-ops`, `lode-cli`, docs.

**Requirements**
- `loded doctor --config C` on the server: configuration parses; data directory writable;
  free disk space (warn below 10%); certificate expiry and last ACME result; the
  `acme_domain` resolves to an address of this machine; last scheduled backup and its age
  against the schedule; database and store reachable. Exit 0, 1 on a failure, 2 on warnings
  only; `--json`.
- `lode doctor [URL]` from a client: DNS answer, TLS handshake and certificate expiry,
  `/info` reachable, server and client versions, signed-in identity.
- The runbook replaces its hand checks with these where they cover the same thing (the
  verification commands stay visible).

**Acceptance:** tests with a test server for each check passing and failing (expired test
certificate, missing backup, full-disk hook); JSON shape documented.

**Out of scope:** fixing problems automatically, checks from outside the network.

## T179 — Size and revisions in `depot list`

**Goal:** `lode admin depot list` shows what the admin web page already shows.
**Depends on:** —.
**Scope:** `lode-server`, `lode-proto`, `lode-ops`.

**Requirements**
- `GET /depots` gains optional `revisions`, `last_commit_at` and, for admins, `size_bytes`
  (from the admin UI's cached size; absent with S3 storage, as on the web page).
- `lode admin depot list` prints a table (name, revisions, size, last commit); `--json`
  carries the fields. Old clients ignore the new fields.

**Acceptance:** handler and CLI tests; a 0.2 client reads the new response.

## T180 — Agent with a token in one command

**Goal:** bootstrap an agent in one command instead of three.
**Depends on:** —.
**Scope:** `lode-ops`, docs.

**Requirements**
- `lode admin agent create NAME --owner U [--with-token] [--grant DEPOT=LEVEL]...`: creates
  the agent, adds the rules, and with `--with-token` creates a token with the agent defaults
  (`read,lock,shelve`, unless `--scope` is given) and prints it once. Built from the existing
  API calls; a failure part way reports what was done.
- Runbook and guide use the one command.

**Acceptance:** CLI test: one command gives an agent that can shelve and cannot commit.

## T181 — Optional Prometheus `/metrics`

**Goal:** teams that already run Prometheus can watch Lode.
**Depends on:** —.
**Scope:** `lode-server`, `loded`, docs.

**Requirements**
- `[metrics] enabled = false` by default. When on, `GET /metrics` on the same port in the
  Prometheus text format, readable with a token that has the new `metrics` scope (or from
  addresses in `allow_from`). Counters and gauges the server already has: requests by route
  class and status, commits, blob bytes in and out, open shelves, held locks, webhook
  deliveries and failures, store and database size, certificate expiry, last backup time.
- No new dependency for the text format.

**Acceptance:** off by default (404); with a token or allowed address, the output parses with
a text-format check; refused otherwise.

**Out of scope:** tracing, dashboards.
