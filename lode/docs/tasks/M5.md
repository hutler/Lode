# M5 — Branching, merge, hardening, packaging

## T050 — `branch` and `switch`

**Goal:** work with branches from the client.
**Depends on:** T016, T025.
**Scope:** `lode-client`, `lode-workspace`, `lode-cli`.

**Requirements**
- `lode branch list [--all]`, `lode branch create <name> [--from <branch>[@rev]] [--switch]`,
  `lode branch archive <name>`.
- `lode switch <branch>`: fetch the target head manifest, diff against workspace rows, apply
  with the update algorithm (local modifications are carried over and merged; conflicts as in
  update). Locks held on the old branch are reported, not moved.
- `status` and prompts show the current branch.

**Acceptance**
- Create a branch, switch, commit there; `main` is unchanged; switching back restores `main`
  content exactly.
- Switch with a local modification to a file identical on both branches keeps the edit;
  to a file that differs produces a merge or conflict.

**Out of scope:** merge.

## T051 — `merge` and `merged_from`

**Goal:** basic branch merge with recorded origin.
**Depends on:** T050.
**Scope:** `lode-server` (merge-info query), `lode-workspace`, `lode-cli`.

**Requirements**
- Server: `GET /depots/{d}/branches/{b}/merge-info?source=<branch>` returning the branch
  point and the merged ranges from `rev_merge` along the target's ancestry, plus the computed
  merge base per SPEC §5.4.
- `lode merge <source>`: apply `base → source head` to the workspace (ARCHITECTURE §10.5);
  requires no pending conflicts; records the pending range. `lode merge <source> -r N`
  applies the single change `N-1 → N` and records range `N..N`.
- `status` shows the pending merge; `commit` sends `merged_from`; `revert --merge` abandons it,
  and `revert --all` does so too. `shelve` carries the pending merge into the shelf and
  `unshelve` restores it (T033).
- The server already validates and stores `merged_from` (T014); `log -v` shows it.
- Document the known limit: after a single-revision pick, a later full merge re-applies that
  change (usually a no-op merge, sometimes a conflict). Smarter skipping is a later module.

**Acceptance**
- Feature branch with three commits merges into `main`; the commit records the range; a
  second `merge` with no new source commits reports nothing to do.
- New commits on the source after a merge: the next merge applies only those.
- Divergent edits to one text region conflict; binary divergence conflicts.
- `-r N` applies exactly that revision's changes and records `N..N`.

**Out of scope:** merge tracking per file, streams, rename-aware merge beyond what
`copy_from` records allow trivially.

## T052 — `blame`

**Goal:** per-line history.
**Depends on:** T015, T026.
**Scope:** `lode-server`, `lode-cli`, `lode-mod-mcp`.

**Requirements**
- `GET /depots/{d}/blame?rev=&path=`: for a text file, each line's last-changing revision,
  author and time, computed by walking the path's history (following `copy_from`) and diffing
  successive versions. Cache results by `(path, blob id)` in a bounded in-memory cache.
  Binary file → `invalid_request`. Cap on history depth with a `truncated` flag.
- `lode blame <path>[@rev]` and an MCP `blame` tool.

**Acceptance**
- Known history fixture produces the expected attribution, including across a rename and
  across a branch point.

**Out of scope:** ignoring whitespace, move detection inside files.

## T053 — Admin CLI

**Goal:** administer a server without touching the database.
**Depends on:** T019, T022.
**Scope:** `lode-cli`, `lode-client`.

**Requirements**
- `lode admin depot create|list`, `user create|list|disable|passwd`, `agent create|list|disable`,
  `group create|add|remove|list`, `token create|list|revoke [--for <principal>]`,
  `acl list|add|remove`, `gc [--dry-run]`, `fsck [--full]`.
- Token values are printed once, to stdout only, never logged.
- `acl add` validates globs and prints the resulting effective access for a sample
  `--check <principal> <branch> <path>`.

**Acceptance**
- Scripted setup of a depot with two users, a group, an agent and ACL rules entirely through
  the CLI, then verified by behaviour (who can read/commit what).

**Out of scope:** web admin UI.

## T054 — Hardening

**Goal:** prove the robustness claims of SPEC §10.
**Depends on:** T025.
**Scope:** tests across crates; fixes where tests fail.

**Requirements**
- Crash tests: using T027 failpoints, abort the server at each step of the commit path and
  during GC; restart; `fsck` passes and the client's retry behaves per spec.
- Client crash tests: kill `checkout`, `update` and `commit` at random points; rerun converges.
- Concurrency soak: many clients committing, updating, locking and shelving for a bounded
  time; invariants checked at the end (no lost update, linear revisions, locks exclusive).
- Fuzz targets (`cargo fuzz` or property tests) for tree decoding, object header parsing,
  path validation, `.lodeconfig` parsing and manifest parsing on the client.
- Hostile-server tests for the client and hostile-client tests for the server: path traversal,
  oversized fields, decompression bombs, wrong hashes, slow bodies (timeouts).

**Acceptance**
- All of the above run in CI (soak and fuzz in short bounded form; long form documented).
- Every defect found is fixed with a regression test, or listed in the report.

**Out of scope:** third-party security audit.

## T055 — Packaging and operator docs

**Goal:** something a team can install.
**Depends on:** T028.

**Requirements**
- Release workflow building `lode` and `loded` for Linux (x86_64, aarch64; static musl),
  Windows (x86_64) and macOS (x86_64, arm64), with checksums.
- Container image for `loded` running as a non-root user with a volume for the data dir.
- systemd unit and a Windows service wrapper or documented alternative.
- Bring `docs/user-guide.html` in step with actual behaviour (commands, config keys, error
  messages) and regenerate `docs/Lode-User-Guide.pdf` by printing it with a headless browser.

**Acceptance**
- Manual: fresh machine install from release artifacts following the guide reaches a first
  commit. Container starts, persists data across restarts, passes a smoke test in CI.

**Out of scope:** OS package repositories, installers.

## T056 — Acceptance and performance pass

**Goal:** confirm v1 meets the spec.
**Depends on:** all other tasks.

**Requirements**
- End-to-end scenario suite covering each section of SPEC §5–7 once.
- Benchmarks for the three numeric targets in SPEC §10, with results recorded in
  `docs/BENCHMARKS.md` (hardware, dataset, numbers). Profile and fix if a target is missed,
  or report why not.
- Review that locks, shelves and MCP use only the module surface (no back doors).
- Update SPEC and ARCHITECTURE to match what was built; list every deviation.

**Acceptance**
- Scenario suite green on all three platforms. Benchmark report present.

**Out of scope:** new features.
