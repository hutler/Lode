# M16 — Lode 0.4: streams and smarter merge

Group 3 of the v2 candidates in the plan "Lode after v1": branch types with rules for which
way changes flow (streams, as Perforce has them), and merges that need less hand work. The
person asked on 2026-11-20 to "execute all what we got in plan"; M15 was group 2.

Ground rules for every task in this milestone:

- **Opt-in.** A branch without a stream type behaves exactly as in 0.3, and so does any merge
  where either side has no type. Existing depots need no change after upgrading.
- Merge history stays what v1 stored (`merged_from` ranges); streams add rules on top of it,
  not a new history format.
- Nothing from a depot's `.lodeconfig` runs a program on a person's machine. A depot may name
  a merge tool; only the person's own `settings.toml` says which command that name runs.
- Every new error is a documented code with a `details.reason`, so the CLI, MCP and Lode Desk
  can explain it the same way.

## T160 — Stream types and flow rules on the server

**Goal:** a branch can be a mainline, development or release stream, and the server refuses
merges that go the wrong way.
**Depends on:** T055 (merge), T152 (portable SQL).
**Scope:** `lode-meta`, `lode-proto`, `lode-server`, docs.

**Requirements**
- Branch rows gain `stream_type`: `mainline`, `development`, `release` or none (migration 7,
  SQLite and Postgres forms; existing branches get none). The stream parent is the branch's
  existing parent (`parent_branch_id`).
- `BranchView.stream` (`{type}`, absent when none). `POST …/branches` takes an optional
  `stream`; `PATCH …/branches/{b}` takes `stream` to set or clear the type (depot admin).
  Rules: `mainline` only on a branch without a parent; `development` and `release` need a
  parent that has a type. Breaking a rule is `invalid_request` with
  `details.reason = "stream_parent"`.
- **Flow rules**, checked for every `merged_from` range on commit and on shelf submit, when
  both the target and the source have a type:
  - *Merge down* (source is the target's parent): allowed into a development stream. A
    release stream takes only single-revision picks from its parent (`from_rev == to_rev`).
  - *Merge up* (source is a child of the target): allowed from a release stream. A development
    stream may *copy up* only when it is up to date with its parent: the merge base of
    parent→child is the parent's head at commit time.
  - *Sideways* (any other pair): refused.
  A refusal is `conflict` with `details.reason = "stream_flow"`, `details.direction`
  (`merge_down`, `merge_up`, `copy_up`, `sideways`) and, for copy up, `details.behind` (parent
  revisions not yet merged down).
- `force_flow: true` on the commit or submit request skips the rules for a depot admin (scope
  `admin`); it is recorded in the `revision.created` event data as `forced_flow: true`.
- `GET …/merge-info` adds `flow: {direction, allowed, reason?, behind?}` (`direction` is
  `untyped` when either side has no type), so clients can warn before applying a merge.
- Branch list, show and the admin web UI's depot page show the type.
- Docs: SPEC §5.3a (new: streams), ARCHITECTURE §5.3 (rules), CLI-JSON error reasons.

**Acceptance**
- Server tests for each direction: allowed merge down into development; release refuses a
  full merge down and accepts a pick; merge up from release; copy up refused while behind
  (with `behind`) and allowed after merging down; sideways refused; untyped pairs unchanged;
  `force_flow` by an admin passes, by a writer is `permission_denied`.
- The same rules apply to a shelf submit carrying `merged_from`.
- Migration 7 on SQLite and Postgres; a 0.3 database opens and every branch has no type.

**Out of scope:** virtual streams, stream specs that narrow paths, re-parenting a branch.

## T161 — Streams in the command line

**Goal:** people create and see streams, and `lode merge` explains the flow before it
touches the workspace.
**Depends on:** T160.
**Scope:** `lode-client`, `lode-ops`, `lode-cli`, `lode-mod-mcp`, docs.

**Requirements**
- `lode branch create NAME --type development|release [--from …]`;
  `lode branch set-type NAME mainline|development|release|none`.
- `lode branch list` prints the type, and `lode branch tree` prints the stream tree with each
  stream's pending merges (merge down and merge up counts from `merge-info`). JSON: `tree`
  as nested `{name, type, head_rev, down, up, children}`.
- `lode merge SOURCE` reads `flow` first: a refused flow stops before any file is written
  (`stream_flow`, same details as the server), with a hint such as "merge `main` into
  `dev/ui` first (3 revisions behind)". `--force-flow` passes it on to the commit.
- `lode commit --force-flow` for admins; the commit JSON has `forced_flow`.
- MCP: `branch_list` includes `stream`; `merge_info` includes `flow`.
- Docs: user guide section "Streams", CLI-JSON.

**Acceptance**
- CLI tests: create a mainline/development/release tree, `branch tree` JSON shows the counts;
  `merge` from a sibling is refused before touching files; copy up while behind fails with the
  hint and succeeds after merging down; a release takes `merge -r N` from its parent.

## T162 — Rename-aware merge

**Goal:** a file renamed on one side and edited on the other merges into the renamed file
instead of coming back under its old name or ending in a delete conflict.
**Depends on:** T055.
**Scope:** `lode-client`, `lode-ops`, docs.

**Requirements**
- Renames are the `copy_from` + delete pairs that commits already record. `lode merge`
  collects the source range's renames from revision history (`GET …/revisions/{n}` changes)
  and the workspace's own renames since the merge base (its pending `copy_from` rows and the
  target branch's history after the base).
- *Renamed there, edited here:* the source's delete of the old path and add of the new path
  become one change: the local edits are merged three-way into the new path (base = old
  content at the base, mine = local old path, theirs = new path) and the old path is removed.
- *Renamed here, edited there:* the source's modify of the old path is applied to the local
  new path, three-way as usual.
- *Renamed differently on both sides:* a conflict that keeps both names (outcome
  `rename_conflict`), resolvable with `lode resolve --mine|--theirs`.
- Applies to `merge`, and to `unshelve` where the shelf records `copy_from`. Directory renames
  are handled file by file. A rename found only by content (no `copy_from`) is out of scope.
- New outcome `renamed` in the merge JSON, with `from`.

**Acceptance**
- CLI tests for the three cases with text files, a binary renamed there and unchanged here,
  and a rename chain (a→b→c) inside the merged range.

## T163 — Structure-aware merge for JSON

**Goal:** two people adding different keys to the same JSON file merge without a conflict.
**Depends on:** T055.
**Scope:** `lode-core` (config), `lode-ops`, docs.

**Requirements**
- `.lodeconfig` `[merge] json = ["**/*.json", …]` (default: `**/*.json` and `**/*.uproject`,
  `**/*.uplugin`). When the line merge of a matched file conflicts, Lode parses base, mine and
  theirs and merges objects key by key: a key changed on one side takes that side, the same
  change on both sides is fine, different changes to the same scalar or array are a conflict.
  Arrays merge as a whole value.
- The result keeps mine's key order, adds new keys from theirs after their neighbour, and is
  written with mine's indentation and line endings (detected; two spaces when unknown) and a
  final newline when mine had one.
- On a structural conflict, or when any side does not parse, the file is left with the usual
  line conflict markers. JSON outcome `merged` with `strategy: "json"`.
- Used by `update`, `merge` and `unshelve` (the three-way paths share one function).

**Acceptance**
- Unit tests: disjoint key additions, nested objects, same change twice, scalar conflict,
  array conflict, unparsable side, key order and indentation kept, CRLF kept.
- CLI test: two workspaces add different keys to a `.uproject`; the second update merges.

**Out of scope:** YAML, TOML and XML (the function is written so a format can be added).

## T164 — External merge tools

**Goal:** binary and special formats can be merged with the tool made for them, started by
Lode with the right files.
**Depends on:** T055.
**Scope:** `lode-core` (config), `lode-ops`, `lode-cli`, docs.

**Requirements**
- `.lodeconfig` `[merge.tools] "**/*.uasset" = "unreal"` names a tool per path pattern. The
  person's `settings.toml` says what a name runs:
  `[merge_tools.unreal] command = ["UnrealEditor.exe", "-diff", "{base}", "{mine}",
  "{theirs}", "{merged}"]`, `trust_exit_code = true`. Placeholders are replaced in single
  arguments; no shell is involved.
- `lode resolve PATH --tool [NAME]` writes base, mine and theirs to `.lode/tmp/merge/…`, runs
  the tool, and on success (exit 0 when `trust_exit_code`, otherwise the merged file changed)
  takes `{merged}` as the resolution. `lode resolve --tool` with no path walks every
  conflicted path that has a tool.
- `lode merge` and `update` never start a tool by themselves; their output names the tool for
  each conflicted path (`tool` in JSON) and suggests `lode resolve --tool`.
- A tool name without a command in settings is reported (`merge_tool_unknown`) with the
  settings snippet to add. `lode merge-tool list` shows names, patterns and whether each is
  set up.
- Docs: user guide "Merge tools", with examples for Unreal, KDiff3 and Beyond Compare.

**Acceptance**
- CLI tests with a scripted test tool (a small binary built by the test kit that writes a
  chosen result and exit code): success resolves, failure leaves the conflict, an unchanged
  merged file with `trust_exit_code = false` leaves it, unknown name reported, no tool runs
  during `merge`.

## T165 — Lode Desk: streams and merge tools

**Goal:** Lode Desk shows the stream tree and the flow rules, and starts merge tools.
**Depends on:** T161, T164.
**Scope:** `lode-desk`.

**Requirements**
- The branch sidebar groups branches as a stream tree with a type badge and pending
  merge-down/up counts; "Merge from parent" and "Copy up to parent" actions are enabled only
  when the flow allows, with the reason as a tooltip otherwise.
- The conflict view gets "Open in merge tool" for a path that has a configured tool.
- New branch dialog: type picker (none, development, release).

**Acceptance**
- Desk tests on the view model: tree grouping, action states for each direction, the tool
  button's presence; manual check on Windows recorded in `desk-acceptance.md`.
