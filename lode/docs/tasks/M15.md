# M15 — Lode 0.3: chunked large files, Postgres, caching proxy

Group 2 of the v2 candidates in the plan "Lode after v1": what a team needs once its assets
are large and the team is bigger or spread over several offices. Asked for by the person on
2026-11-14 ("The later v2 groups: chunked large files, Postgres, a caching proxy and more").
Group 3 (streams, smarter merge) follows as M16.

Ground rules for every task in this milestone:

- A **file's id never changes**: it stays `BLAKE3(content)` whether the server keeps the file
  whole or in chunks. Trees, revisions, locks, shelves, obliterate, caches and every client
  out there keep working, and an old client can still download a chunked file whole.
- SQLite stays the default database and the filesystem the default storage. Postgres and the
  proxy are opt-in settings; a server that sets neither behaves exactly as 0.2.
- Every new setting appears commented in the default `loded.toml`, in the admin web UI's
  Settings page, and in the user guide.
- No dependency that needs a C toolchain beyond what the workspace already needs.

## T150 — Chunked storage on the server

**Goal:** the server can keep a large file as a list of content-defined chunks, so a small
edit to a 2 GB file stores only the changed chunks.
**Depends on:** T123.
**Scope:** `lode-core`, `lode-proto`, `lode-store`, `lode-server`, `loded`, docs.

**Requirements**
- **Chunker** in `lode-core` (no I/O): FastCDC (2020 paper, normalized chunking level 2)
  with a fixed gear table derived from BLAKE3 (entry `i` = the first 8 bytes of
  `BLAKE3("lode gear v1" || u8 i)`, little-endian), minimum 256 KiB, average 1 MiB, maximum
  4 MiB. The parameters are part of the protocol (`/info` reports them as
  `chunking: {algorithm: "fastcdc-2020-lode-v1", min, avg, max, threshold}`), so every
  client cuts the same file at the same places. Written as a streaming state machine
  (`push(&[u8]) -> boundaries`), with property tests: boundaries are independent of how the
  input is split into pushes, and every chunk respects min and max.
- **Chunk list object** (kind 3, reserved since §3.3): payload `u8 version = 1`,
  `varint count`, then per chunk `[32] id` and `varint size`; canonical decoding (count ≥ 2,
  sizes within min..max except the last, which may be smaller; trailing bytes rejected).
  Stored under the **file's** id. Each chunk is an ordinary blob (kind 1) under its own id.
- **Upload:** `PUT /depots/{d}/blobs/{id}/chunks` with the chunk-list encoding as body
  (scope `write` or `shelve`, like upload). The server checks every chunk is stored
  (`missing_objects` lists the absent ones), then streams the chunks in order through BLAKE3
  and compares with `id` (`hash_mismatch` on a difference) before publishing the list with
  the same no-replace rule as blobs. A file stored whole already is `AlreadyPresent`.
  Obliterated ids are refused (`obliterated`).
- **Download:** `GET /depots/{d}/blobs/{id}` works for both forms and assembles a chunked
  file on the fly (with `Range` on raw bytes, which chunks make cheap). `GET
  …/blobs/{id}/chunks` returns the chunk list for a chunked file and `not_found` with
  `details.reason = "not_chunked"` for a whole one. `objects/missing` counts a chunked file
  as present.
- Files below `threshold` (16 MiB, same constant as the text/binary cut-off) are never
  chunked; the server refuses a chunk list for a smaller file (`invalid_request`).
- **Maintenance:** GC marks the chunks of every reachable chunk list. fsck checks that every
  chunk exists; `--full` re-hashes the assembled file. Obliterating a chunked file deletes
  the list and every chunk that no other surviving chunk list or tree uses, and refuses
  later uploads of the list or of any of those chunks as a whole file. Backup and
  `migrate-storage` copy chunk lists like any object. Blame, `cat`, MCP and diff read through
  the same reader, so they see the whole file.
- S3 storage gets the same behaviour unchanged; a chunked file is no longer limited by the
  5 GiB single-`PUT` cap.
- Docs: ARCHITECTURE §3.3–3.5 (chunk list format, chunker), §6 (routes), §11 (GC, fsck,
  obliterate); SPEC §8 (built); CLI-JSON if any output changes.

**Acceptance**
- Chunker property tests (split independence, bounds) and a fixed-vector test: a seeded 64 MiB
  input gives a recorded list of boundaries (the vector goes in the docs for other clients).
- A 40 MiB file uploaded as chunks downloads byte-identical, whole and with `Range`; a chunk
  list whose chunks are missing is refused with their ids; a wrong id is `hash_mismatch`.
- A second version that changes 1 MiB in the middle stores at most 3 new chunks.
- GC keeps chunks of reachable files and removes those of an unreachable list after the grace
  period; fsck reports a missing chunk; obliterate removes the file's own chunks and keeps
  chunks shared with another file.
- The same suite runs against the filesystem store and the fake S3.

**Out of scope:** chunking small files, cross-depot dedup, changing chunk parameters per depot.

## T151 — Chunked transfer in the client

**Goal:** committing a small edit to a large file uploads only the changed chunks; an
interrupted upload or download resumes where it stopped.
**Depends on:** T150.
**Scope:** `lode-client`, `lode-workspace`, `lode-ops`, `lode-cli`, `lode-desk` (progress
text only), docs.

**Requirements**
- Commit and shelve: a file at or above the server's `threshold` is cut with the shared
  chunker while it is hashed (one read). `objects/missing` is asked for the chunk ids, only
  missing chunks are uploaded (in parallel, as blobs are today), then the chunk list is sent.
  A server without `chunking` in `/info` gets whole uploads as before.
- Resuming uploads needs no state: a rerun asks `objects/missing` again.
- Checkout, update, switch and revert: for a large file the client asks for the chunk list,
  takes the chunks it already has from (in order) the shared download cache, the local file
  at the row's `base_id` when it is unmodified (cut with the same chunker to find them), and
  downloads the rest into `.lode/tmp/chunks/` before assembling into `.lode/tmp` and checking
  the file id. A rerun after an interruption reuses the chunks already in `.lode/tmp/chunks/`.
- The shared cache (`LODE_CACHE_DIR`) stores chunks of large files instead of whole large
  files, so two versions of a 2 GB asset cost little more than one.
- Progress counts bytes actually sent and received, and reports bytes reused, in the CLI and
  in Lode Desk; `--json` results of commit, shelve, checkout and update gain
  `bytes_uploaded`/`bytes_downloaded` and `bytes_reused`.
- Docs: ARCHITECTURE §10 (transfer, cache), the user guide (what chunking gives, nothing to
  set), CLI-JSON.

**Acceptance**
- A 200 MiB generated binary is committed; changing 1 MiB in the middle and committing again
  uploads under 10 MiB (measured from the server's request log in the test).
- A second workspace updating to that change downloads under 10 MiB.
- An upload killed half way (client crash point) and rerun sends only the remaining chunks;
  the same for a download.
- Against a server without chunking (simulated), commit and checkout still work whole.
- `lode cat` and Lode Desk's binary diff of the chunked file work.

**Out of scope:** chunking files below the threshold, delta compression inside chunks.

## T152 — Metadata behind a database layer

**Goal:** prepare `lode-meta` for a second database without changing behaviour: every SQL
statement in the server and its modules goes through one small layer that can speak to
SQLite and, in T153, Postgres.
**Depends on:** —.
**Scope:** `lode-meta`, `lode-server`, `lode-mod-*`, docs.

**Requirements**
- `lode_meta::Db` replaces direct `rusqlite::Connection` use outside `lode-meta`: `execute`,
  `query_one`, `query_opt`, `query_all` (and a streaming form for big scans) with typed
  parameters (`i64`, `&str`, `&[u8]`, `Option<…>`, `bool`) and a `Row` getter. Statements
  are written once in a portable subset: numbered `?1` parameters (rewritten to `$1` for
  Postgres), `RETURNING` instead of `last_insert_rowid()`, `ON CONFLICT … DO NOTHING/UPDATE`
  instead of `INSERT OR IGNORE/REPLACE`, no SQLite-only functions. Where a statement truly
  differs, the layer offers `dialect()` and both forms sit side by side.
- Module migrations become a pair of files per step (`.sqlite.sql`, `.postgres.sql`); core
  migrations likewise. Existing SQLite databases migrate with no change on disk (the SQLite
  files stay as they are).
- The single-writer design stays: one write connection, serialized writers, read pool.
- ARCHITECTURE §4.1 and §8 describe the layer and the rule for modules.

**Acceptance**
- The whole test suite passes unchanged on SQLite.
- A lint test fails if a crate other than `lode-meta` names `rusqlite` (the workspace client
  database in `lode-workspace` and `lode-ops` is excluded; it stays SQLite).
- An existing 0.2 data directory opens and serves after the change (fixture test).

**Out of scope:** Postgres itself (T153).

## T153 — Postgres metadata backend

**Goal:** a server can keep its metadata in Postgres instead of SQLite, for many concurrent
users and for a standby server that can take over.
**Depends on:** T152.
**Scope:** `lode-meta`, `lode-server`, `loded`, CI, packaging (compose file), docs.

**Requirements**
- `[database] kind = "postgres"` with `url` or `url_file` (a file holding the URL, so the
  password is not in `loded.toml`); TLS to the database with rustls (`sslmode=require` or
  `verify-full`), no OpenSSL. Postgres 14 or newer.
- Driver: `postgres` / `tokio-postgres` with `tokio-postgres-rustls` (justify in the report;
  they are the maintained pure-Rust drivers). Reads use a small pool; writes keep the single
  serialized writer, so commit semantics are unchanged.
- **One active server per database:** `loded serve` takes a Postgres advisory lock at start
  and refuses to serve while another server holds it ("database in use by <host>"). A standby
  started with `--wait-for-lock` waits and takes over when the active one stops or dies
  (Postgres frees the lock with the connection). The blob storage must be shared between them
  (S3, or a shared filesystem); the docs say so.
- `loded migrate-db --config <file> --to postgres --url-file <f>` copies every core and module
  table from SQLite into an empty Postgres database in one transaction, checks the row counts,
  then switches `loded.toml` (keeping `loded.toml.before-postgres`), like `migrate-storage`.
- Backup with Postgres copies `loded.toml` and the objects and writes `pg_dump` instructions
  instead of a database copy (`database_external` in the report); fsck, GC, obliterate and the
  admin UI work unchanged (the Overview shows "Postgres" and the server version instead of
  the database file size).
- CI runs the server and module test suites a second time against Postgres (service
  container on Ubuntu) through `LODE_TEST_POSTGRES`; locally the tests skip without it.
- Packaging: a `compose.postgres.yaml` example with `loded` and Postgres.

**Acceptance**
- The server, module and CLI scenario suites pass against Postgres.
- The concurrency test (N clients committing) passes against Postgres with a valid serial
  history.
- A second `loded serve` on the same database refuses to start; with `--wait-for-lock` it
  takes over within seconds after the first is killed, and clients continue.
- `migrate-db` moves a data directory with commits, locks, shelves, webhooks and checks;
  the result passes fsck and serves the same history.

**Out of scope:** several active servers at once, read replicas, other databases.

## T154 — Caching proxy

**Goal:** a small server in a remote office keeps copies of file content, so people there
download each file across the long link once.
**Depends on:** T151.
**Scope:** `lode-server` (proxy module and one upstream endpoint), `loded`, `lode-client`,
`lode-ops`, `lode-cli`, `lode-desk` (settings field), packaging, docs.

**Requirements**
- `loded proxy --config proxy.toml` runs a proxy: `[proxy] upstream = "https://lode.example.com"`,
  `cache_dir`, `cache_max_gib` (default 100), and the same `[server]`/`[tls]` listener settings
  as `loded serve` (including Let's Encrypt). `loded setup --proxy` writes such a file, and
  `loded service install` works for it.
- It serves `GET /api/v1/depots/{d}/blobs/{id}` (whole or with `Range`) and
  `…/blobs/{id}/chunks`, from its cache or by fetching once from the upstream (concurrent
  requests for the same object share one fetch), verifying every object's hash before keeping
  it. A chunked file is cached chunk by chunk. `GET /api/v1/info` answers with the upstream's
  info plus `proxy: {upstream, version}`. Every other path answers `not_found` with a hint to
  use the main server.
- **Access stays with the upstream.** The proxy never stores tokens. For each caller (keyed
  by a hash of the bearer token) and depot it asks the upstream once whether the caller may
  read the depot, and keeps the answer for 60 seconds. It keeps each depot's obliterated ids
  from a new endpoint `GET /api/v1/depots/{d}/obliterated-ids?after=` (depot readers; ids only,
  no paths or reasons), refreshed every 60 seconds, refuses those with `obliterated` and
  deletes cached copies. So a revoked reader or an obliterated file reaches the proxy within a
  minute; the docs say so.
- Client: the user setting `proxy` (per server, in `settings.toml` under `[proxies]`), the
  variable `LODE_PROXY`, and `lode proxy set|clear|show` route content downloads through the
  proxy and everything else to the server. If the proxy fails (network error or 5xx) the client
  warns once and downloads from the server. Lode Desk has the field in its server settings.
  `lode status --remote` and `--json` outputs name the proxy in use.
- Cache: LRU by last use, evicted to the cap after each fill, safe across restarts, and
  checked by hash on read (a damaged entry is dropped and fetched again). `loded proxy
  --prefetch <depot>[:branch]` (optional, also as `[proxy] prefetch = […]`) downloads the head
  of a branch after each new revision, polling the upstream's revision list.
- Metrics on the proxy's `/admin/` page: cache size, hit rate, bytes saved, upstream errors.
- Packaging: the proxy runs from the same `loded` binary and installers; a compose example.
- Docs: ARCHITECTURE (new section on the proxy), the user guide (setting up an office proxy,
  what it caches, how long a revocation takes), the admin guide.

**Acceptance**
- With an in-process upstream and proxy: a checkout through the proxy downloads each blob from
  the upstream once; a second workspace checks out with no upstream content traffic.
- A caller without read access to the depot is refused by the proxy; a revoked caller is
  refused once the 60-second window passes (time injected).
- An obliterated file is refused through the proxy after the next refresh and its cached copy
  is gone.
- A damaged cache entry is fetched again; the cache stays under its cap.
- With the proxy down, the client warns and downloads from the server.
- Chunked files through the proxy reuse cached chunks.

**Out of scope:** caching uploads or metadata, write-through commits, several proxy levels.
