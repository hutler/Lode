# M18 — The agent as a desktop client

Lode already treats agents as principals with their own tokens, MCP on the server and in a
workspace, and provenance on every shelf and commit. This milestone lets an agent do through
`lode mcp` what a person does in Lode Desk, and lets it notice what changed on the server
without polling. Lode Desk stays the place where a person reviews; the agent does the
mechanics and proposes by shelf. (M16 is kept for v2 group 3, M17 for the deployment
feedback, whose tasks use T170–T181.)

The analysis behind it, checked against `main` (12cd8f7), is summarised in "Why" below.

Ground rules for every task in this milestone:

- **No new concepts.** No agent scheduling, no agent-to-agent messaging, no built-in LLM
  calls, no separate "conflict proposal" object: the shelf is the proposal. New MCP tools are
  thin wrappers over functions `lode-ops` already has for the CLI and Lode Desk.
- **Same rules as today.** Paths stay confined to the workspace (`outside_workspace`);
  `commit` stays listed only for tokens with `write`; events carry identifiers only
  (ARCHITECTURE §8.1); the server MCP endpoint stays stateless.
- Every tool answers the same JSON as the matching `--json` command, documented in
  [`CLI-JSON.md`](../CLI-JSON.md); [`MCP.md`](../MCP.md), SPEC §6.4 and the user guide gain
  the matching text.

## Why

| Gap | On `main` | Task |
| --- | --- | --- |
| The agent cannot switch, merge, resolve or see locks in a workspace | `lode mcp` has 14 tools (status, diff, add, remove, move, revert, update, lock, unlock, shelve, unshelve, commit, log, read_file_at_revision). `status` is called with `remote: false` hard-coded. `lode-ops` already has `branch`, `switch`, `merge`, `locks`, `changelist`, `resolve`, `conflict_sides` and `resolve_with`. | T190, T191 |
| No conflict flow for agents | Covered once T191 is in: a shelf made during a pending merge carries the merge origin and its submit records `merged_from` (SPEC §6.2). | T191 |
| The agent is blind to events | The server writes every event to the outbox (`lode-server/src/events.rs`) and wakes subscribers through `AppState::outbox_notify`; only webhooks read it. Nothing lets a client wait for or list events. | T192, T193 |
| Unattended agents with `write` can land unreviewed work | Per-branch `deny write` already blocks direct commits and self-submitted shelves (a submit commits as the caller), but only one principal or group at a time. | T194 |
| Workspace watch mode | Not built: MCP clients act once per turn and do not wake the model on server notifications. T190's `status` summary is the agent's reconcile step instead. | — |
| Large files from workspace-free agents | Not in this milestone. M15 (chunked upload) is now on `main`, so a `blob` field on MCP edits plus a `lode blob put` helper can follow as its own task when wanted. An agent in a workspace already shelves large files with no inline limit. | later |

## Order

```
M18  T190  T192  T194                 (independent of each other)
     T191                             (after T190)
     T193                             (after T192)
```

T190 and T191 are worth the most per line and come first; T192 and T193 can run in parallel
with them. T194 is small and can land any time, but before anyone runs unattended agents with
`write`.

## T190 — `lode mcp`: see what a person sees

**Goal:** the agent starts each turn with the picture Lode Desk's status bar and side panels
give a person.
**Depends on:** —.
**Scope:** `lode-cli` (`src/cmd/mcp.rs`), `lode-ops` (status summary), docs.

**Requirements**
- `status` gains `remote: bool` (default `false`, as today), passed to `lode-ops` status
  `--remote`: newer versions at head, deleted at head, who holds each lock in scope.
- `status` answers a `summary` in every case:
  `{ "changed", "needs_lock", "conflicted", "untracked", "pending_merge": bool }`, plus with
  `remote` `{ "newer_at_head", "locked_by_others", "head_rev" }`. Counts only; the file list is
  unchanged. `lode status --json` gains the same `summary`.
- New tools, each listed for every token that can read:
  - `branches { archived?: bool }` — `lode branch list`.
  - `locks { paths?: [string], mine?: bool }` — `lode locks` for the workspace's branch.
  - `conflicts { path?: string, max_bytes?: int }` — without `path`, the conflicted files
    with `text: bool` and `theirs_rev`; with `path`, that file's sides from
    `conflict_sides`: `base`, `mine`, `theirs`, `result`, `theirs_file`. Text sides are cut
    at `max_bytes` (default and maximum 256 KiB, as `read_file`) and say so; binary sides
    give size only.
- Tool descriptions say when to use each (for example: call `status` with `remote` before
  editing files that need a lock).

**Acceptance**
- MCP tests in `lode-cli/tests/mcp.rs`: `status` with `remote` names a file locked by
  another user and a file newer at head; the summary counts a changed file that needs a lock;
  `branches` and `locks` match the CLI's JSON; `conflicts` returns three sides for a text
  conflict, ids only for a binary one, and a cut side over `max_bytes`.
- A path outside the workspace is refused `outside_workspace` for `locks` and `conflicts`.

**Out of scope:** tools that change the workspace (T191); `checkout`.

## T191 — `lode mcp`: switch, merge, resolve and changelists

**Goal:** the agent can move between branches, merge, settle conflicts and group work, and a
person accepts the result as a shelf.
**Depends on:** T190.
**Scope:** `lode-cli` (`src/cmd/mcp.rs`), docs.

**Requirements**
- New tools (all change only the workspace; anything they send to the server is a read):
  - `switch { branch, rev? }` — `lode switch`.
  - `merge { branch, rev? }` — `lode merge`; the answer lists conflicts as the CLI does.
  - `resolve { path, take: "mine" | "theirs" }` or `resolve { path, text | base64 }` — the
    first is `lode resolve --mine|--theirs`, the second `resolve_with` (content at most
    16 MiB, like `create_shelf`'s inline limit; larger is `too_large`). Marks the file resolved.
  - `changelist { action: "new" | "list" | "move" | "delete", name?, description?, paths? }` —
    `lode changelist`.
- `update` keeps its behaviour; its answer, like `switch` and `merge`, says which files
  conflicted so the agent knows to call `conflicts`.
- MCP.md gains "Merging and conflicts": merge or update, `conflicts`, `resolve` each file,
  `shelve` with a description of each choice, a person reviews in Lode Desk and submits.
  For a binary conflict the agent can only take one side and says which in the description.
- MCP.md gains "A working day" with the three requests from the vision prompt mapped to tool
  calls (switch and log; status with remote then lock; changelist and shelve).

**Acceptance**
- MCP test: switch to another branch and back; merge with one text and one binary conflict,
  resolve the text one with new content and the binary one with `theirs`, shelve; the shelf
  carries the merge origin and, submitted by a person, records `merged_from` and author =
  agent, submitter = person.
- `commit` is still not listed for a token without `write`, and `resolve` with both `take`
  and content is refused `invalid_request`.

**Out of scope:** `checkout` (a person creates the workspace once; the target folder lies
outside any workspace); `view` changes; Lode Desk changes.

## T192 — Event feed on the server

**Goal:** any client can wait for "something happened in this depot" with one cheap request.
**Depends on:** —.
**Scope:** new module crate `lode-mod-feed`, `lode-server` (registration, config),
`lode-proto`, `lode-client`, docs.

**Requirements**
- Module `feed`, on by default (`[modules] feed = true`). It subscribes to the outbox like
  webhooks and copies each event into its own table
  `feed_event (id, depot_id, branch_id NULL, kind, created_at, payload)`, keyed by the outbox
  id. Kept for `[feed] keep_days` (default 7) and at most `keep_events` per depot (default
  100 000); pruning runs with the existing maintenance pass. SQLite and Postgres forms of the
  migration (as M15 T152/T153 do).
- `GET /api/v1/depots/{d}/events?after=<id>&kinds=<k,…>&wait=<seconds>`:
  - Answers `{ "events": [envelope…], "next": <id>, "truncated": bool }`, envelopes exactly
    as ARCHITECTURE §8.1, at most 500 per answer, oldest first.
  - Without `after`: no events and `next` = the newest id, so a client starts from now.
  - `after` older than the oldest kept event: `truncated: true` and the kept events from the
    oldest; the client re-reads the revision list, as webhook receivers do.
  - `wait` (default 0, at most 55) holds the request until a matching event arrives or the
    time runs out, woken by `outbox_notify` after the feed has stored the event; then answers
    as above (possibly empty). At most `[feed] max_waiting` (default 256) held requests per
    server; beyond that `wait` is treated as 0.
  - Needs scope `read` and read access to the depot; events on branches the caller cannot
    read at all are left out. `kinds` takes the event names of §8.1; an unknown name is
    `invalid_request`.
- `lode-client` gains `Client::events(depot, after, kinds, wait)`.
- `lode events <depot> [--after ID] [--kinds K,…] [--wait S] [--follow] --json` for scripts;
  `--follow` loops and prints one JSON line per event (NDJSON), resuming from `next`.

**Acceptance**
- Handler tests: an event appears after a commit, a lock and a shelf; `wait` returns early on
  an event and empty on timeout; `after` past retention gives `truncated`; a reader of one
  branch does not see events on a branch denied to them; a token without `read` is refused.
- The feed survives a restart without losing or repeating events (cursor and table in the
  same transaction).
- With `[modules] feed = false` the route is `not_found` and the outbox prunes as before.

**Out of scope:** streaming (SSE or WebSocket); Lode Desk and chat notifications using the
route (follow-ups; T175 in M17 can use it); events for paths or content.

## T193 — `wait_for_events` on the MCP endpoints

**Goal:** an agent runtime sitting in a loop can react to a new shelf, a released lock or a
new revision.
**Depends on:** T192.
**Scope:** `lode-mod-feed` (server tool), `lode-cli` (`lode mcp` tool), docs.

**Requirements**
- Server `/mcp` tool `wait_for_events { depot, after?, kinds?, timeout_s? }` with the answer
  of T192. `timeout_s` default 25, at most 50, to stay under common MCP client tool
  timeouts. Listed for every token with `read` when the module is on.
- `lode mcp` lists the same tool for the workspace's depot (`depot` optional there), calling
  the server through `lode-client`.
- The tool description tells the agent to keep `next` and pass it as `after`, and to fetch
  details with `log`, `get_shelf` or `list_locks`.
- MCP.md gains "Watching a depot": the loop, what each event means and which tool reads its
  details, and that the loop belongs to the agent runtime, not to Lode.

**Acceptance**
- Server MCP test: `wait_for_events` returns a `shelf.created` made by another user within
  the timeout, and empty after it; `lode mcp` test does the same for `revision.created`.
- The endpoint stays stateless: two requests with the same `after` to a fresh server
  instance give the same answer.

**Out of scope:** pushing MCP notifications to clients; any server-side agent scheduling.

## T194 — An access-rule subject for all agents

**Goal:** one rule keeps every agent's work going through shelves on chosen branches.
**Depends on:** —.
**Scope:** `lode-meta`, `lode-proto`, `lode-server` (`perm`, admin web UI), `lode-ops`, docs.

**Requirements**
- Access rules take a new subject `agents`, matching every principal of kind `agent`:
  `lode admin acl add deny write agents --depot game --branch main`. Stored like `all`
  (subject kind, no id); no other schema change.
- `acl list`, `acl check` (with `decided_by`) and the admin web UI's access page show it; the
  web form offers it beside "everyone".
- An older client listing rules sees the subject as text and does not fail (check
  `lode-proto` deserialisation; add an `Other(String)` fallback if needed).
- SPEC §5.5 and §7.1 and the admin guide gain a "Keep agents on shelves" recipe: deny write
  on protected branches for `agents`, so agents still read and shelve (not lock: a lock needs
  write access) and a person
  submits.

**Acceptance**
- With the rule, an agent with `write` cannot commit to `main` (`permission_denied`) nor
  submit its own shelf there, can still shelve, and can commit to another branch; a
  user is unaffected.
- The admin web UI test adds and removes such a rule.

**Out of scope:** a `.lodeconfig` setting for the same thing (access rules stay the one
place that says who may write where).
