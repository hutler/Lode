# M6 — Integration

Features that let outside systems, such as a build server, work with Lode: notifications,
reported results, a gate on shelf submit, and client features for unattended machines.
Everything here is generic; no outside system is named or depended on.

M6 can run alongside M5. Both new modules are off by default and must use only `ModuleCtx`
and the `Module` trait (AGENTS.md).

## T060 — Webhooks module (`lode-mod-webhooks`)

**Goal:** signed HTTP notifications for depot events.
**Depends on:** T017, T022.
**Scope:** `lode-mod-webhooks`, `lode-proto`, `lode-client`, `lode-cli`, `loded` (wiring).

**Requirements**
- Tables, admin API, enqueue-in-`on_event`, delivery worker, headers, signature, retry
  schedule, URL rule and retention exactly per ARCHITECTURE §9.4. Event envelope and payloads
  per §8.1.
- The worker starts with the server, resumes pending deliveries after a restart, and stops
  cleanly on shutdown. Backoff is computed from the injected clock.
- Retry schedule: 10 s, 1 min, 5 min, 30 min, then hourly until 24 h after the first attempt.
- Secrets are stored so they can be used for signing, are returned only by the create call,
  and never appear in logs or in the deliveries listing. Request bodies are stored for retry;
  they contain identifiers only.
- `[webhooks] allow_http` in `loded.toml`; without it, creating a hook with an `http://` URL
  is `invalid_request`.
- `lode admin webhook add <depot> <url> --events e1,e2 [--branch GLOB]`, `list`, `remove`,
  `deliveries <id>`, `ping <id>`; `add` prints the secret once.
- `/info` shows the module when enabled.

**Acceptance**
- A test receiver gets one request per matching event, with a valid signature over the exact
  body, the right `X-Lode-Event`, and the same `X-Lode-Delivery` across retries.
- Events not in the hook's list, or on branches outside its pattern, are not sent.
- A receiver that fails then recovers gets the delivery on a later attempt; one that never
  recovers ends `failed` after 24 h (clock-driven test); meanwhile a second hook keeps
  receiving, and the outbox still prunes.
- A server restart with pending deliveries loses none.
- Redirect responses are not followed and count as failures.
- Payloads contain no paths and no content.
- With the module disabled, no routes or tables exist and nothing is sent.

**Out of scope:** per-user hooks, payload templates, receiving webhooks.

## T061 — Checks module, server (`lode-mod-checks`)

**Goal:** store and list results reported by outside systems.
**Depends on:** T017, T040.
**Scope:** `lode-mod-checks`, `lode-proto`, `loded` (wiring).

**Requirements**
- Table, `POST` and `GET` endpoints, limits, scope `checks` (declared through
  `Module::scopes()`, not an agent default) and the `check.updated` event per
  ARCHITECTURE §9.5.
- Reporting is an upsert on (target, name): state, summary, url, reporter and time are
  replaced. Revision targets must exist (`not_found` otherwise); shelf targets are stored
  without validation and need a `version` of 1 or more.
- Listing returns reporter name and kind with each check, newest first.
- A token with only `checks` and `read` cannot commit, shelve, lock or administer.

**Acceptance**
- Report, update and list for a revision and for two versions of one shelf; versions do not
  share results.
- Reporting without the `checks` scope → `permission_denied`. Invalid name, state, oversized
  summary or non-http url → `invalid_request`.
- `check.updated` is written once per report.
- With the module disabled: endpoints absent; a token that carries `checks` still works for
  its other scopes.

**Out of scope:** the gate (T062), running anything, check history.

## T062 — Submit gate

**Goal:** require passing checks before a shelf is submitted to protected branches.
**Depends on:** T061, T035.
**Scope:** `lode-mod-checks`, `lode-core` (`.lodeconfig` `[checks]` section).

**Requirements**
- Parse `[checks]` (`branches` globs, `required` list of `{name, reporter}`) in the
  `.lodeconfig` parser. An entry without `reporter` is invalid, which makes the file
  unparseable and therefore uncommittable (T014).
- `pre_commit` per ARCHITECTURE §9.5: applies only when `origin` is the shelves module and the
  branch matches; reads the shelf id and version from `origin` and the rule from the branch
  configuration in `CommitCtx`; consults only its own table; rejects `checks_required` with
  `details.missing` listing each unmet name and why (absent, not `success`, wrong reporter).
- The module must not depend on `lode-mod-shelves`. The only coupling is the documented
  origin name `"shelves"` and attribute keys `shelf_id`, `shelf_version`.
- If the checks module is enabled and the shelves module is not, the gate is inert.

**Acceptance**
- Submit with every required check `success` from the named reporter succeeds.
- Refused when a check is missing, `pending` or `failure`; when it was reported by a
  different principal; and when it passed on an earlier version of the shelf.
- A shelf that edits `.lodeconfig` to drop the requirement is still gated by the head's rule.
- A direct commit to the same branch is not gated. A client that puts shelf ids into
  `extensions` gains nothing.
- A branch outside `branches` is not gated.

**Out of scope:** gating direct commits, shelf-only branches, admin bypass.

## T063 — Checks in the client and for agents

**Goal:** let people and agents see check results.
**Depends on:** T061, T028, T041.
**Scope:** `lode-client`, `lode-cli`, `lode-mod-checks`.

**Requirements**
- `lode checks <rN | shelf-id[@version]>` lists name, state, reporter, time, summary and
  link; without a shelf version it uses the shelf's current one. `--json` per T028. Works
  without a workspace when `--server` and `--depot` are given.
- `lode shelf submit` explains a `checks_required` rejection by listing the unmet checks.
- MCP tool `list_checks` contributed through `mcp_tools()` (scope `read`).
- No other command or module changes its output because of checks.
- Clear message when the server reports the module is not enabled.

**Acceptance**
- CLI output and JSON covered by snapshot tests. `list_checks` appears on the MCP endpoint
  only when the module is enabled.
- A refused submit prints the unmet check names and exits with code 1.

**Out of scope:** a command for reporting checks (reporters use the HTTP API).

## T064 — Client features for unattended machines

**Goal:** make a reused, scripted workspace cheap and safe to drive.
**Depends on:** T050, T028.
**Scope:** `lode-client`, `lode-workspace`, `lode-cli`.

**Requirements**
- `lode switch <branch> -r <rev>`: go directly to that revision of the branch without first
  syncing its head. `<rev>` must be in the branch's history.
- `LODE_SERVER` and `LODE_TOKEN_FILE` honoured by every command, taking precedence over a
  stored login; a missing or unreadable token file is an authentication error (exit code 3).
  No variable carries the token itself. The token file's path is never written into the
  workspace.
- `lode --version --json` → `{"ok":true,"version":"…","api":"…"}`.
- Shared download cache per ARCHITECTURE §10.1: `LODE_CACHE_DIR` or user setting `cache_dir`;
  used by checkout, update and switch; verified by hash on read (a corrupt entry is deleted
  and re-downloaded); copy into the workspace, never link; size cap (default 20 GiB) with LRU
  eviction; safe under concurrent processes.
- Document the reset sequence for a reused workspace in `docs/CLI-JSON.md`:
  `revert --all`, `clean`, `switch <branch> -r <rev>`.

**Acceptance**
- `switch B -r N` from an arbitrary state produces the same tree as a fresh checkout of B
  at N, and transfers no blob that is not part of N (assert via the test server).
- With the two variables set and no stored login, commands authenticate; with a stored login
  for another account, the variables win.
- Two workspaces of one depot sharing a cache download each blob once in total. Two processes
  populating the cache concurrently leave it consistent. A file modified in a workspace
  leaves the cache entry intact. A corrupted cache entry is detected and replaced.
- The reset sequence from a deliberately damaged workspace (modified, added, deleted,
  untracked, conflicted, pending merge) reaches the exact target state.

**Out of scope:** reflinks, a network proxy cache.
