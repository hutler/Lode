# M11 — GUI branches, merges, setup and release

Lode Desk covers the rest of a team's day: moving between branches, merging them and resolving
what does not merge, choosing which part of a large depot is on disk, opening a revision or a
file from a link, and installing and updating the app itself. The milestone ends with a user
guide and an acceptance run. Plan: "Lode after v1" (2026-11-14). As before, everything goes
through `lode-ops`, so the app and `lode` agree on every rule and error.

## T110 — Branches and switch

**Goal:** see the depot's branches, create one and move the workspace between them.
**Depends on:** T093.
**Scope:** `lode-desk`.

**Requirements**
- The sidebar's branch line opens a branch picker: active branches with head revision and
  where each started, the current one marked, a text filter, and "Show archived".
- Create a branch from the current branch at the workspace's revision, or from any branch at
  any revision (`BRANCH@REV`), optionally switching to it.
- Switch to a branch (its head, or a revision). Local changes are carried over; files that do
  not merge are left in conflict and the Changes view shows them. Locks held on the old branch
  stay there, and the app lists them after the switch.
- A switch or update that did not finish (`update_incomplete`) says to finish it and offers
  the button that does.
- Archive a branch after asking (depot admin; `permission_denied` otherwise).
- Every open view (Changes, History, Locks, Shelves) follows the new branch.

**Acceptance**
- Rust tests: list, create (with and without switching), switch carrying a local change, and
  archive, through the app's commands against a test server.
- UI tests for the picker, creating with switch, the locks-left notice, and archiving.
- Screenshots of the picker and the create dialog.

**Out of scope:** deleting branches (Lode archives them).

## T111 — Merge and three-way conflicts

**Goal:** merge a branch and resolve what does not merge without a terminal or an editor.
**Depends on:** T110.
**Scope:** `lode-desk`, `lode-ops` (reading a conflict's three sides).

**Requirements**
- Merge from another branch: everything since the merge base, or one revision (`-r`). The
  result lists each file's outcome (applied, merged, conflicted, unchanged, skipped).
- While a merge waits for the next commit, the Changes view says which merge it is, suggests
  the commit message ("Merge BRANCH rA..rB"), and offers to abandon it (`revert --merge`) after
  asking.
- A conflicted text file opens a three-way view: base, mine and theirs, with the differences
  marked, and an editable result that starts from the file with its conflict markers. Take
  mine, take theirs, or save the edited result and mark it resolved. Each conflict region can
  be taken from either side with one click.
- A conflicted binary file or symlink offers mine or theirs, with each side's size (theirs is
  the `*.rREV` file beside it).
- Commit stays disabled while conflicts remain, and says why.

**Acceptance**
- Rust tests: merge with a conflict, reading the three sides, resolving with mine, theirs and
  an edited result, and abandoning a merge.
- UI tests for the merge dialog, the pending-merge notice, taking one region from each side,
  and resolving a binary conflict.
- Screenshots of the merge result and the three-way view.

**Out of scope:** merging across depots; a merge preview before applying.

## T112 — Workspace view editor

**Goal:** choose which part of a large depot is on disk.
**Depends on:** T091.
**Scope:** `lode-desk`.

**Requirements**
- A Workspace section shows the view's include and exclude patterns, how many files and bytes
  the view holds on the server at the workspace's revision, and how many are on disk.
- A folder tree of the depot (one level at a time) with a checkbox per folder: ticking adds an
  include, unticking adds an exclude, and the patterns can also be edited as text.
- Applying a change shows what will be fetched and removed first. Files with local changes
  are kept and named; "drop them anyway" needs a second confirmation (`--force`).
- Applying shows progress and can run while the rest of the app stays usable.

**Acceptance**
- Rust tests: show, include, exclude and the refusal for a changed file, through the app's
  commands.
- UI tests for ticking folders into patterns, the preview, and the refusal.
- A screenshot of the view editor.

**Out of scope:** per-file overrides; views shared between workspaces.

## T113 — `lode://` links

**Goal:** send someone a link that opens a revision, a file or a shelf in their app.
**Depends on:** T093, T102.
**Scope:** `lode-desk`.

**Requirements**
- Links have the form `lode://HOST[:PORT]/DEPOT/rREV`, `lode://HOST/DEPOT/PATH@REV` (or
  `...?branch=NAME`) and `lode://HOST/DEPOT/shelf/ID`, with the server's scheme (`https`, or
  `http` for local servers) given by `?http=1`. Paths are percent-encoded.
- "Copy link" on a revision, on a file in a revision or in history, and on a shelf.
- The app registers the `lode` scheme with the system on install, and a second launch hands its
  link to the running app instead of opening another window.
- Opening a link picks an open or recent workspace of that server and depot (asking when there
  are several) and shows the revision, the file's history at that revision, or the shelf. With
  no workspace for it, it offers to check the depot out.
- Links are parsed strictly: anything else is refused with a message and never acted on.

**Acceptance**
- Unit tests (Rust and UI) for building and parsing links, including refusals.
- UI tests for copying a link and opening each kind, with and without a matching workspace.

**Out of scope:** web links to a server page (the server has no web UI).

## T114 — Installers and auto-update

**Goal:** install Lode Desk like any other desktop app and keep it current.
**Depends on:** T113.
**Scope:** `lode-desk`, CI.

**Requirements**
- Bundles: Windows MSI and NSIS setup, macOS `.dmg` (universal), Linux `.deb`, `.rpm` and
  AppImage. Each registers the `lode://` scheme.
- Update check at start and once a day, from the release feed on the project's GitHub
  releases, with release notes, "Install and restart" and "Later"; turned off by a setting
  and by the `LODE_DESK_NO_UPDATE` environment variable for managed machines.
- Updates are signed; the app accepts only a package signed with the project's update key.
  The private key never enters the repository: CI reads it from a secret.
- CI builds every bundle on its own system for each tag and attaches them to the release with
  the feed file.
- Code signing for Windows and macOS is wired but off until the project has certificates.

**Acceptance**
- Linux bundles built and installed in CI; the feed file checked against its schema.
- A test that an update signed with another key is refused.
- The release checklist in `docs/release.md` covers the app.

**Out of scope:** an app store listing; delta updates.

## T115 — User guide and acceptance

**Goal:** a guide a new team member can follow, and proof that the app does what it says.
**Depends on:** T110–T114.
**Scope:** `lode-desk`, docs.

**Requirements**
- `docs/desk-guide.md`: install, sign in, check out, the daily loop (changes, locks,
  changelists, commit), history, blame and diff, shelves and review, branches and merges,
  conflicts, the workspace view, links, updates, and what each error means. Screenshots from
  `npm run screenshots`, in light mode.
- An acceptance run that follows the guide against a real server: one Rust test drives the
  app's commands through every section, and a checklist covers what needs a person (installer,
  update, link from another app) on Windows, macOS and Linux.
- The README of `crates/lode-desk` points to the guide.

**Acceptance**
- The acceptance test passes in CI.
- The manual checklist is filled in on Windows (the person's PC) at least.

**Out of scope:** translations.
