# M4 — Agents and MCP

Check the current documentation of the Rust MCP SDK (`rmcp`) and the MCP specification before
starting T041 or T042. Do not rely on remembered APIs; transports and auth details change.

## T040 — Agent identities and provenance

**Goal:** agents as first-class principals with recorded provenance.
**Depends on:** T014.
**Scope:** `lode-server`, `lode-proto`.

**Requirements**
- Agent creation (from T011) gains defaults per SPEC §7.1: new agent tokens get scopes
  `read`, `shelve`, `lock` unless others are requested by an admin. An agent's owner can
  create and revoke its tokens; only admins can grant `write` or `admin`.
- Provenance per SPEC §7.3: the server sets `via` (`api`, `mcp`) and copies the
  client name from `User-Agent` (self-reported, not verified; `via` is `mcp` only for the
  server MCP endpoint); the client-supplied `agent` object is accepted only as
  an object of string fields, total size capped at 4 KiB, stored verbatim.
- Revision views include `author`, `submitter`, each with `kind` (`user`/`agent`) and, for
  agents, `owner`; plus `provenance`.
- Revisions list accepts `author_kind=agent|user` and `author=<name>` filters.
- Disabling a user disables the agents they own.
- Default agent scopes are computed, not hard-coded: `read` plus every scope an enabled module
  declares as an agent default (`shelve`, `lock`). `checks` is not one.

**Acceptance**
- An agent token cannot commit by default (`permission_denied` on scope), can after `write`
  is granted by an admin, and never inherits its owner's ACL access.
- Provenance round-trips; oversized or non-string provenance is rejected `invalid_request`.
- Disabling the owner invalidates agent tokens.

**Out of scope:** MCP.

## T041 — Server MCP endpoint (`lode-mod-mcp`)

**Goal:** read-only MCP tools over streamable HTTP.
**Depends on:** T040, T015, T030, T032.

**Requirements**
- MCP server at `/mcp` using the official Rust SDK, streamable HTTP transport, authenticated
  by the same bearer tokens. Unauthenticated requests get the standard 401.
- Tools (SPEC §6.4, read side): `whoami`, `list_depots`, `list_branches`, `log`,
  `show_revision`, `list_dir`, `read_file`, `diff` (between two revisions, optional path
  filter, unified text diff, size-capped), `search_history` (substring match over messages
  and changed paths, paged), `list_locks`, `list_shelves`, `get_shelf`.
- Each tool: clear description written for a model, JSON Schema input, structured JSON result,
  errors as MCP tool errors carrying the Lode error `code`.
- Every tool goes through the `ModuleCtx` services, so scopes and ACLs apply identically to
  the HTTP API. Tools depending on a disabled module are not listed.
- `read_file`: line range parameters, default cap 256 KiB with a `truncated` flag; binary
  files return `{binary: true, size, id}`.
- All calls set provenance `via = "mcp"`.
- This module defines only the tools that read core data. `list_locks`, `list_shelves` and
  `get_shelf` are defined by their own modules (T030, T032) and reach the endpoint through the
  tool registry (T017). The module hosts whatever the registry holds, filtered by the token's
  scopes; it must not depend on `lode-mod-locks` or `lode-mod-shelves`.

**Acceptance**
- An MCP client (SDK client in tests) lists tools and calls each one against a seeded depot.
- A principal without read access to a path cannot see it through any tool.
- Large file and large diff are truncated with the flag set.
- With locks or shelves disabled, their tools are absent.

**Out of scope:** write tools (T043), blame tool (added in T052).

## T042 — Local MCP server (`lode mcp`)

**Goal:** workspace operations for a coding agent running on a developer machine.
**Depends on:** T028, T031, T033.
**Scope:** `lode-cli`.

**Requirements**
- `lode mcp [-C <workspace>]` speaks MCP over stdio. Tools (SPEC §6.4, local side): `status`,
  `diff`, `add`, `remove`, `move`, `revert`, `update`, `lock`, `unlock`, `shelve`, `unshelve`,
  `commit`, plus `log` and `read_file_at_revision`.
- Tools call the same library functions as the CLI commands and return the same JSON as
  `--json` (T028).
- `commit` is listed only if the stored token has scope `write`; otherwise the tool list
  ends at `shelve`.
- `--agent-model`, `--agent-session`, `--agent-tool` flags (or env vars) populate the
  provenance `agent` object on shelves and commits made through this server.
- All paths in tool input are resolved inside the workspace root; anything outside is refused.
- Nothing is written to stdout except protocol messages.
- Add a short `docs/MCP.md` with setup snippets for common MCP clients.

**Acceptance**
- Scripted MCP session: status → edit a file on disk → diff → shelve; the shelf exists on the
  server with agent provenance.
- A path escaping the workspace is refused.
- With a token lacking `write`, `commit` is not listed and calling it fails.

**Out of scope:** editor plugins.

## T043 — Workspace-free shelves through MCP

**Goal:** let an agent propose changes with no checkout.
**Depends on:** T041, T035.
**Scope:** `lode-mod-shelves` (the tools are contributed through `mcp_tools()`; `lode-mod-mcp`
needs no change).

**Requirements**
- Tools `create_shelf` and `update_shelf` per ARCHITECTURE §9.3. Edits carry full new content
  as `text` or `base64`; `action` is `add`, `modify`, `delete`; `copy_from` supported.
  `base_id` is derived by the server from `base_rev`.
- Limits: at most 500 edits and 16 MiB of inline content per call (configurable); larger work
  must use the HTTP blob API.
- `submit_shelf` tool listed only for tokens with scope `write`; `expected_version` is a
  required input.
- Listed only when the shelves module is enabled and the token has scope `shelve`.
- End-to-end test of the intended workflow: an agent token reads files, creates a shelf; a
  human token reviews it (`lode shelf diff`) and submits it; the revision shows the agent as
  author and the human as submitter.

**Acceptance**
- The workflow test above passes.
- An edit to a path the agent cannot read → `not_found`; exceeding limits → `too_large`.
- `update_shelf` by a different principal is refused.

**Out of scope:** server-side merge or rebase of shelves, semantic search.
